# 打卡水印相机 (Android)

拍照时把 **地点 / 日期 / 时间 / 单位 Logo** 烙进照片里的原生 Android 应用。
水印版式参考「今日水印相机」：黄色「打卡」标签 + 大号时间的白色卡片，下方跟地点与日期。

白卡片**宽度按内容自适应**（约半屏宽），不是一条从左通到右的长横幅 —— 见 3.5。

**默认不含经纬度**（经纬度、定位精度、海拔有开关，收在「高级」里，默认全关）。

---

## 一、在 GitHub 上编译（不用装 Android SDK）

1. 新建一个仓库，把本目录所有文件推上去（`.github/` 也要推，否则不会触发构建）：

   ```bash
   git init
   git add .
   git commit -m "打卡水印相机"
   git branch -M main
   git remote add origin https://github.com/<你的用户名>/<仓库名>.git
   git push -u origin main
   ```

2. 推送后自动开始编译。到仓库页面的 **Actions** 标签看进度，第一次大约 3~5 分钟。

3. 编译成功后，点进那次运行，页面底部 **Artifacts** 里下载：
   - `watermark-camera-debug` —— 调试包
   - `watermark-camera-release` —— 正式包

   下载下来是 zip，解压出 `.apk`，传到手机上点一下就能装。
   （手机需要允许「安装未知来源应用」。）

   也可以手动触发：Actions → 构建 APK → Run workflow。

> 两个包都用 debug 签名，都能直接安装。要上应用商店的话，把 `app/build.gradle.kts`
> 里 `signingConfig = signingConfigs.getByName("debug")` 换成你自己的 keystore。

## 二、在本机编译（可选）

需要 JDK 17+ 和 Android SDK（platform 36 / build-tools 36.0.0）：

```bash
# 在项目根目录建 local.properties，指向你的 SDK
echo "sdk.dir=/path/to/android-sdk" > local.properties

./gradlew assembleDebug        # 产物: app/build/outputs/apk/debug/app-debug.apk
./gradlew assembleRelease -x lintVitalRelease   # 产物: app/build/outputs/apk/release/app-release.apk
```

**两个包都要出。** 改完代码只跑 `assembleDebug` 会漏掉 release —— 交付目录里那个 release
会悄悄停在上一个版本，而这次的差异只在图上两个字上，装上基本看不出问题，
但"防伪"这个改动就永远不会到手里。

release 没有开混淆与资源裁剪（`isMinifyEnabled = false` / `isShrinkResources = false`），
也照样用 debug 签名，所以两个包都能直装；体积差（约 8.6MB vs 12.1MB）来自可调试位与
APK 压缩策略，不是代码差异。

**`-x lintVitalRelease` 不要省。** `assembleRelease` 会拉上 `lintVitalRelease` 做全量
Lint 分析，本机实测这一项跑了 **29 分钟还没结束**（debug 构建根本不跑它，所以对比特别刺眼）。
而这个工程里 Lint 配的是 `abortOnError = false` —— 它拦不住任何问题、也不改变 APK 字节，
纯粹让人干等。跳过它 release 构建回到分钟级。真想看 Lint 就单独跑 `gradlew lint`。
（历史版本的 release 也不含 Lint 结果，跳过它得到的包与之前一致。）
CI（`.github/workflows/build.yml`）里那条构建命令也带同一个 `-x` —— 两边行为一致，
免得"本机能出、CI 卡住"。

本仓库没有带 gradle wrapper 的 jar 包，所以本地构建要么用系统装的 `gradle`（8.14.3），
要么先执行一次 `gradle wrapper` 生成 wrapper。

**JDK 必须钉在 17，而且别指望临时 `export JAVA_HOME`。**

`gradle.properties` 里已经写死了一行 `org.gradle.java.home=D:/jdk-17`。
这不是洁癖 —— 本机的 `JAVA_HOME` 指向的是**另一个 JDK**（实测 jdk-22），
用它跑 gradle 会在**配置阶段**就炸掉，任何 task 都执行不到：

```
Could not configure services using BuildScopeServices.configure().
Caused by: java.lang.ClassCastException: class jdk.internal.loader.ClassLoaders$PlatformClassLoader
  cannot be cast to class java.net.URLClassLoader
  at org.gradle.initialization.DefaultJdkToolsInitializer.initializeJdkTools
```

这报错**长得像 Gradle/AGP 版本不兼容**（`initializeJdkTools` 是 Gradle 内部类，
报错栈里全是 Gradle 自己的东西），很容易误导你去翻 `build.gradle`、降 Gradle 版本。
真因只有一个：**跑 gradle 的那个 JDK 不是 17**。

判据：**7 秒内失败 + 一条 `BUILD FAILED` + 一个 task 都没执行** —— 真编译错误不会这么快。
（`--no-daemon` 救不了：它只是 fork 一个单次 JVM，仍然读 `JAVA_HOME`。）

## 三、怎么用

| 位置 | 作用 |
|---|---|
| 顶部左 | **地点**（点击就地修改，超 12 字截断成 `…`）+ 左侧小圆点表示定位状态（绿=已定位／黄=定位中／红=未授权） |
| 顶部右 | 已拍张数、闪光灯开关（见 3.7）、⚙ 设置 |
| 底部左 | 最近一张（点开用系统看图器看） |
| 底部中 | 快门 —— 拍完**自动存到相册** `Pictures/打卡水印相机/`，右下角弹「分享」 |
| 底部右 | 前后摄像头切换 |
| **画面上的水印** | **点地点那行**改地点、**点日期行或卡片里那串时间**改日期时间（见 3.12）；按住会亮一层底，点空白处不拦事件（照常点屏对焦） |

> 定位状态一律用短词（`已定位` / `定位中` / `未授权` / `不可用`），状态由左侧小圆点的颜色共同表达
> —— 这行是常驻的，写长了会把地点挤掉。
>
> 顶部栏里**地点胶囊是 `0dp + weight=1`，吃剩余宽度**，右侧三个控件的位置由它们自己决定。
> 早先写的是 `wrap_content + maxWidth=190dp`，地点一长整行的需求宽度就超过屏宽，
> LinearLayout 把 ⚙ 顶到了屏幕外 —— 现象就是「地点长的时候设置图标只显示一半」。

### 3.1 在拍照界面直接填地点

**点水印上的地点行**，或者点顶部左那颗胶囊 —— 两条路开的是同一个弹窗，**不用退到设置页**：

- **手输任意地点**，或者点下拉箭头选最近填过的（自动记住最近 12 个）
- 点「用当前定位反查」调系统 Geocoder 回填地名，回填后还能再改
- 「清空」只清空输入框、**不关窗**（通常是笔误，想重填）
- 确定后**预览上的水印立刻变**，并自动把「显示地点」打开
  —— 否则填了却看不见，只会让人以为没生效

### 3.1.1 地点会自动精简成 `市+区县·小区`

反查几乎不会给你一个能用的地名，它给的是这种：

```
云岭省星海市云山区湖滨街道风和苑3栋2单元501室
```

顶满一行、字号被压小。所以存之前统一过一遍 `Addr.compact`（`Addr.kt`）：

| 输入 | 输出 |
|---|---|
| `云岭省星海市云山区湖滨街道风和苑3栋2单元501室` | `星海市云山区·风和苑` |
| `北京市朝阳区望京SOHO` | `北京市朝阳区·望京SOHO` |
| `上海市浦东新区张江镇` | `上海市浦东新区·张江镇` |
| `星海市风和苑` | `星海市·风和苑` |
| `风和苑` / `DEMO PARK` | **原样返回**（认不出行政层级就别动） |

剪掉的：省（`xx省`／`自治区`）、街道/镇/乡前缀、**居委会层级（`xx社区`／`xx村委会`）**、
楼栋单元室层门牌、括号补充、方位词与「附近」；小区名超过 10 字截断加 `…`。

居委会那一条要**放在楼栋之后**削：`阳光社区2栋3单元501室` 先被削成 `阳光社区`，
此时它后面已经没有字了，就不会被继续削空 —— 整串就叫「阳光社区」的是一个小区名，一个字都不能动。

| `云岭省星海市云山区青溪镇湖滨社区风和苑商业广场` | `星海市云山区·风和苑商业广场` |
| `星海市洛川区阳光社区2栋3单元501室` | `星海市洛川区·阳光社区` |
| `阳光社区` / `幸福村委会` | **原样返回**（整串就是一个名字） |

原则是**只削，不猜**：认不出市/区县层级，且细节一个字都没削掉，就原样返回 ——
宁可长一点，也不能把一个用户没写过的地名编出来。这条有断言看着（`AddrTest`），
网页版同一个函数用 `verify_addr_parity.js` 对拍，两边逐条一致。

**套娃修复**：线上出现过水印显示成 `星海市云山区·云岭省星海市云山区黄…` ——
「上一次的精简结果」被拼上了「这一次的原始长串」。原因是只剥一层行政前缀不够
（串里有两次「省市区县」），以及 `一个特别特别长的小区` 里的「小区」被县级正则
当成了「…区」吃掉了。现在：先按 `·` 切段、末段若能剥出**市+区县两级**就丢掉前面那截，
再**循环剥**行政前缀直到剥不动，并对 `小区/园区/社区/校区…` 这类词尾设了黑名单。
截断会丢信息（所以"一次→二次"允许去掉省略号后重算），但二次之后必然收敛。

### 3.2 横屏

横屏**能用，不是"勉强"**：

- 旋转手机即自动横屏（`fullSensor`，跟随设备方向，不受系统「自动旋转」开关限制）
- 控件收进**右侧一条竖栏**（设置／翻转／快门／最近一张），不压在画面上
- 地点与张数留在左上角
- 相机画面按 4:3 居中显示，水印浮层**精确贴合画面矩形**（不是屏幕矩形）
- 横屏拍出的照片方向正确（旋转后会自动更新相机 `targetRotation`）

### 3.3 Logo 选不上怎么办（已修）

之前选完图会弹「Logo 读取失败」。**根因是对同一个 URI 开了两次流**：一次 `inJustDecodeBounds`
量尺寸，一次真正解码。相册、云盘、第三方文件管理器给的 `openInputStream` 未必可重复打开，
第二次拿到的是空流 —— `decodeStream` 会安静地返回 null，日志里连异常都没有，所以极难查。

现在改成**只开一次流**：整张图先读进内存，之后量尺寸、解码都在内存里做。
（这也是 `BitmapFactory` 官方推荐的用法 —— `decodeStream` 对不可 mark/reset 的流行为不稳定。）

顺带补的三件事：

| 改动 | 解决什么 |
|---|---|
| 解码优先走 `ImageDecoder`（API 28+） | 能解 **HEIC/HEIF**（现在手机拍照的默认格式，`BitmapFactory` 在部分机型解不出来），并自动应用 EXIF 方向 |
| 强制 `ALLOCATOR_SOFTWARE` | ImageDecoder 默认出 HARDWARE 位图，既不能 `compress()` 成 PNG，也画不到软件 Canvas 上（会直接抛异常） |
| 失败原因分档返回 | 不再只丢一句"失败"，而是明确说：`没有读取该文件的权限` / `打不开这个文件` / `文件是空的` / `图片超过 24MB` / `这个格式解不了（试试 PNG / JPG）` / `写入失败` |

另外还有一个隐性问题一并修了：配置里记着 `logoPath`、文件却被清理软件或卸载删掉了，
会一直"设了 Logo 但照片上没有"。现在读不到就把陈旧路径清掉，不会一直挂着。

选图后的解码也挪到了后台线程，大图不会卡住界面；成功后 toast 里会带上实际像素尺寸。

### 3.4 定位信息有多精简

| 位置 | 之前 | 现在 |
|---|---|---|
| 顶部胶囊 | `已定位 ±8m` | `已定位` |
| 地点对话框状态行 | `已定位 ±8 米，可点下面按钮反查地名` | `已定位 ±8 米` |
| 水印 · 经纬度 | `30.274083°N  120.155092°E`（6 位） | `30.2741°N  120.1551°E`（4 位 ≈11 米，打卡够用） |
| 水印 · 精度与海拔 | 两行：`定位精度 ±8 米` + `海拔 12 米` | 一行：`±8m  海拔12m` |

设置页（⚙）里能改：

- **卡片标签** —— 黄色方块里的字，默认「打卡」，可改成「巡查」「交接班」等
- **单位 / 公司名称** —— 显示在卡片右侧
- **公司 Logo** —— 选一张图（PNG 透明底最好），压到 400px 宽存在本机；**设了 Logo 就优先显示 Logo，不显示单位文字**
- **地点** —— 手填，或者点右侧 📍 按 GPS 反查；填过的地点会进下拉列表，工位固定的话不用每天重敲
- **时间是否到秒**、**显示日期与星期**、**显示备注**、**显示打卡人**、**显示卡片**
- **水印位置** —— 画面底部 / 画面顶部
- **高级** —— 经纬度、定位精度、海拔、前置镜像保存（默认全关）

### 3.5 白色条幅：宽度跟着内容走

参考图里那条白条只到画面中间（约 50% 宽），而旧版是 `w - 2*pad` —— **撑满整行**，
右边留一大块空白，看着像横幅而不是卡片。

现在宽度是算出来的：

```
卡片宽 = 内边距 + 「打卡」标签 + 间距 + 时间 + 间距 + 右侧块(Logo/单位) + 内边距
```

- 右侧块贴的是**卡片右内边距**，不是屏幕右边 —— 卡片短了，Logo 也跟着进来
- 算出来超过 `画面宽 - 2*边距` 时，**先缩时间字号**（78→30，每步 2），而不是让卡片溢出
- 卡片高度同时从 150 压到 116（1080 基准）：150 时白条又高又空，时间字反而显小
- 黄色「打卡」块改成上下各留 8、圆角 11 的近方形块，贴着卡片高度

内容短（没 Logo、没单位）时白条就短，长（带 Logo）时才变长 —— 这是刻意的，
不是"没对齐"。有两条断言钉住这件事（`条幅宽度_*`）：带 Logo 必须比不带宽，
且**都不许超过满宽的 75%**（防以后改回撑满）。

**正文行的两条宽度上界**（`measure()` 里取较小值）：

| 上界 | 1440 宽下的实测值 | 为什么 |
|---|---|---|
| 品牌区左边界 − 间隙 − 边距 | 1030.33 | 两块现在**并排**、底边对齐（见 3.11），不挡就会压到品牌名上 |
| 卡片宽（= 时间条） | 763.67 | 「地点不要超过上面的时间条」—— 用户明确要的 |

```
时间条宽=763.67  行宽上界=763.67  逐行宽=[521.0, 398.0]  品牌区左边界=1086.33
```

两条都只是**上界**：够宽时字号一动不动，只有真超标的那一行才缩。
第二条只在**卡片真有时间大字**时才算数 —— 关掉时间后卡片会缩到只剩「打卡」标签那么宽
（带单位时实测 462.67），照它去卡会把正常的短地名也逼到最小字号。

下限是**名义字号的 45%**（不是 66%）。原来写 66%，但长地名缩到 66% 仍然放不进
上面那两条上界，结果就是"字号是变小了、却照样越过时间条压进品牌区" ——
用户要的那条要求等于没兑现。现在让「放得下」优先，45% 是最后的可读性防线：

```
29 字地名：行字号 26.67（名义 56 的 47.6%）→ 行宽 754.0 ≤ 上界 763.67   ← 真放得下了
```

配色上「打卡」标签是**琥珀黄底 + 深色字**（`#FFC107` / `#14181D`）。
字必须跟着改深色：黄底上压白字的对比度只有 1.9:1，等于看不见。

### 3.6 地点自动显示（不用每次手点「反查」）

定位到手就自动反查地名并填上。三条约束，缺一条都会出问题：

| 约束 | 为什么 |
|---|---|
| **用户自己填过就不覆盖** | 手输「风和苑」是他要的固定值，不能被自动结果冲掉 |
| **最多自动查两次**（首次定位 + 首次高精度 ≤100m） | 定位每 2~5 秒回调一次，不节流会把系统 Geocoder 拖死 |
| 地名没变不写盘 | 免得白刷一遍 UI |

「谁说了算」用一个 `addrManual` 标记表达，不需要额外的按钮：

| 操作 | 标记 | 之后的行为 |
|---|---|---|
| 手输地点 | manual | 定位变化**不再**自动覆盖 |
| 点「用当前定位反查」 | auto | 仍跟着定位更新（内容是机器给的，不算你的选择） |
| 点「清空」 | auto | 回到自动模式 —— 于是「清空」就是「恢复自动获取」的入口 |

万一 ROM 的 Geocoder 不好使，反查会返回 null，此时保持原样、不编一个地名。

### 3.7 顶部闪光灯开关（三档循环）

顶部栏（横屏是右侧竖栏）有一个闪光灯按钮，单击循环三档：**关 → 拍照时闪 → 补光常亮**。

不做「自动」档 —— 打卡场景要的是确定性：自动档什么时候闪说不准，拍完才发现没闪就晚了。

为什么要三档而不是一个开关：只给「开 / 关」时，用户点了「开」却发现灯不亮，
既无从判断是没生效、没触发，还是硬件本来就没有。常亮档走的是
`CameraControl.enableTorch()`，**和拍照闪光不是同一条底层路径**：

| 档位 | 底层 | 图标 | 现象 |
|---|---|---|---|
| 关 | `flashMode = OFF` + `enableTorch(false)` | 灰色斜杠闪电 | — |
| 拍照时闪 | `flashMode = ON` | 黄色闪电 | 只在快门瞬间亮一下 |
| 补光常亮 | `enableTorch(true)` | 黄色灯泡 | 一直亮着，肉眼立刻可验证 |

- 档位会记住（`Prefs.flashMode`），旧版本的布尔值会迁移过来，不丢用户的选择
- 前置摄像头一般没有闪光灯，这时按钮**置灰不可点**，不会静默失效
- 切换前后摄会重建 `ImageCapture`，所以 `applyFlashState()` 必须在每次 bind 之后重跑 ——
  否则表现为「切一下摄像头闪光灯自己关了」
- 离开界面（`onPause`）会强制关掉常亮档，避免切后台/锁屏后手电筒还亮着

**「点了开、图标亮了、拍照却不闪」是怎么修的**：根因是闪光灯参数只靠 bind 之后的
`imageCapture.flashMode = …` 设置，而部分 ROM 只在 session 配置阶段读一次该参数、
运行时单独 set 不触发 session 重建，参数就白设了。现在改成**两处都设** ——
`ImageCapture.Builder().setFlashMode(…)` 让参数进 session 配置，同时 toggle 后
**重建一次 session** 确保底层真的收到。预览会黑一下，是刻意的：总比「点了没反应」强。

### 3.8 备注与打卡人：为什么要带彩色标签

原来的实现里，这两行都是 34f、常规体、纯白、左对齐，唯一区别只有「打卡人：」这个前缀
—— 在图上根本分不清哪行是哪行，问「备注和打卡人显示在哪里、好像没什么区别」很正常。

现在每行前面加一个**琥珀黄小标签**（`备注` / `打卡人`），正文保持白色：

```
备注      设备运行正常
打卡人    张三
```

标签用的是和「打卡」块同一个黄（`LABEL_BG`），所以视觉上是同一套语言。
「打卡人：」那个硬拼进正文的前缀已经去掉了 —— 它是**标签**，不该变成内容的一部分
（否则用户想改文案时得从正文里把「打卡人：」删掉）。

**另一个坑（这是最初"看不见"的真正原因）**：填了内容**不等于**会显示。
`showNote` / `showName` 默认是关的，两个条件都满足才画。现在改成：
**首次填入内容时自动打开对应开关**（和地点那条逻辑一致 —— 填了却看不见，
用户只会以为没生效）。

只在**从空变非空**这一刻自动开，所以用户之后主动关掉它，下次进来保存不会被重新打开
—— 否则这个开关等于关不掉。

### 3.9 右下角品牌区（三行）与防伪码

右下角三行、右对齐、字号逐行变小（顶部模式时在右上角）：

```
                                        今日水印
                                 相机 ▢真实可验▢
                             防伪 5H3HXQ9UL72SS9
```

第三行的标签是**「防伪」两个字**，不是「防伪码」—— 后面跟的那 14 位就是码本身，
再挂一个「码」字是重复；字号小的时候也少占一个汉字位（约 31px @ s=1.333）。

初版是把品牌名和标语拼成一行、防伪码另起一行 —— 那样读起来是一串没有重点的长字
（`打卡水印  相机真实可验  防伪码 XXXX`）。三样东西性质本来就不同：主标识 / 说明 / 校验码，
分行加递减字号本身就是层级，一眼能分清哪是名字、哪是那串码。

品牌名与标语都能改（设置页），也可以整块关掉。基准字号 **40 / 28.6 / 23**（1080 基准），
层级比 1 : 0.71 : 0.575；某一行超宽时**只缩它自己**（下限 0.62 倍且不小于 13s），
层级不会被一张长标语搅乱。

> **绝对大小不是从参考图量出来的。** 那张 360×165 的裁切只能反解**行与行的比例**
> （1.40，见 `verify/solve_brand.py`）—— 那块裁切在原照片里占多宽，无从得知。
> 所以最初只是沿用了旧版的 30，观感上一直偏小（品牌名 40.0 vs 左侧地点 56.0 @1440）。
> 现在提到 **40**：与地点行的 42 基准齐平略小 —— 官方水印里这两个是同一量级的
> 两个信息块，30 会让右下角显得像附注而不是标识。行2/行3 同步跟随，层级关系不变。

#### 品牌名与标语是矢量稿，不是系统字体

这两个词条是**标识**，不是信息。信息（时间/地点/备注）各手机长得不一样无所谓；
标识不行 —— 换个 ROM 换套中文字体，同一张水印就变了样。

所以它们走**轮廓路径**（`BrandMark.kt` + 自动生成的 `BrandMarkPaths.kt`），
跟着 APK 走，与系统装了什么字体完全无关。标语后面那块浅灰圆角底也是稿子的一部分。

| 做法 | 体积 | 结果 |
|---|---|---|
| 塞一份字体进 `res/font` | +1.4 MB | 也一致，但白搭 |
| **只取用到的 10 个字的轮廓** | **+3 KB** | 一致，且不经过字体引擎 |

顺带去掉一整类风险：矢量不会出现「字体没加载上就悄悄退回系统字体」
（PT Mono 那次就是靠 `document.fonts.check` 才发现根本没生效，肉眼看不出）。

**轮廓从哪来**：`Y:\今日水印相机字体\AlimamaShuHeiTi-Bold.ttf` —— 阿里妈妈数黑体 Bold，
阿里官方发布、免费可商用（官网可下载）。选它的依据是**量出来的** ——
参考图里逐字量出的「墨宽/墨高」比与它一致（±4%），并且它是那个目录里唯一覆盖这 10 个字的
TrueType 字（另两个 CJK 是 CFF 的汉仪旗黑，而且渲出来的字重明显偏轻）。
只有这 10 个字的**轮廓**进了仓库（`BrandMarkPaths.kt`，+3KB），字体文件本身没有分发。

**版式参数也是解方程解出来的**，不是目测（参考图只有 360×175，还没我们自己出图的一个字大）。
字体里每个字的墨迹宽高已知，图上量到的是像素，两者一比就得到每行的字号；各字左边界之差
再给出步进。见 `verify/solve_brand.py`：

| 项 | 反解值 |
|---|---|
| 行1 : 行2 字号比 | **1.40**（图上 72.1px : 51.5px） |
| 行1 字距 | **+0.164 em**（这个词条是放松排的，不是默认字宽） |
| 「相机」→ 灰块 间距 | 0.238 em |
| 灰块留白 | 「真实可验」**墨迹框**四周各 0.15 em |

灰块按**墨迹框**算而不是按基线算：按基线算出来的位置与图上差了 9px，
按墨迹框算上下留白才对得上。

**改了名字/标语会怎样**：那一行退回系统字体渲染（矢量稿只做了内置那 10 个字），
设置页的说明里写明了这一点。

**这套稿子怎么从头重做一遍**（换字体、加字都要走这条链，纯 stdlib，不依赖 fontTools）：

```bash
# 1) 探字体：家族名 / 授权 / 覆盖了哪些字，以及是 glyf 还是 CFF
python verify/detect_font.py info  "Y:/今日水印相机字体/*.ttf"
python verify/detect_font.py chars "Y:/.../AlimamaShuHeiTi-Bold.ttf" 今日水印相机真实可验

# 2) 从参考图反解版式：字号比 / 字距 / 灰块留白（解方程，不是目测）
python verify/solve_brand.py

# 3) 提轮廓 → 生成 Kotlin 数据表（顺序不能反，后者吃前者的 _glyphs.json）
python verify/gen_glyphs.py            # → verify/_glyphs.json
python verify/gen_brand_kt.py          # → app/src/main/java/.../BrandMarkPaths.kt

# 4) 闭环：提取出的路径 vs 同字体 fillText，逐像素比（必须 <0.1%）
python verify/gen_glyphs.py && node verify/glyph_parity.js
```

**第 4 步不能省。** 它验的是「轮廓提取器有没有把字读歪」——自己写的 glyf 解析器最容易错在
隐含中点没补、`loca` 基址忘了加、y 没翻转、复合字形没展开，而这些错误**看起来仍然是汉字**，
肉眼逐字比根本发现不了。没有这一步，你可能拿着一份"能画出来但已经变形"的路径跑好几天。

**字形只能取 glyf（二次曲线）的字体**：`0x00010000` / `true` 是 glyf，`OTTO` 是 CFF（三次贝塞尔）。
本机可用的 CJK 里 `AlimamaShuHeiTi-Bold.ttf` 是 glyf；汉仪旗黑是 CFF，而且渲出来字重明显偏轻。

> 生成器只产 `M` / `L` / `Q` / `Z` 四种**绝对坐标**命令，所以 Android 侧不需要通用 SVG
> 路径解析器（也就不需要 `androidx.core.graphics.PathParser` —— 那个类跨版本改过好几次 API）。

**它仍然不能证**「这张照片确实是这台设备的相机拍的」 —— 那需要服务端留底。

**防伪码是真的摘要，不是随机数**：`SHA-256(时间到分钟 + 地点 + 备注 + 打卡人 + 单位 + 机型 + 经纬度)`
取前 70 bit，Base32 成 **14 个连续字符**（与参考图位数一致）。不加分隔横线 ——
横线在水印那种小字号下几乎看不见，却白占三个字符位，抄写时人还会自动忽略它、反而更容易看错。

字符集剔掉了 `0 / O / 1 / I` —— 数字字母混排时这四个几乎必抄错。取整 32 个字符，
正好对上 `& 0x1F`，不留偏分布也不越界。

时间**只取到分钟**：预览是每帧重绘的，若把秒算进去，用户看到的预览码和按下快门后
出图的码会不一样 —— 那才是真的"防伪不了"。

| 它能证什么 | 它不能证什么 |
|---|---|
| 照片上的水印字段**自洽** —— 拿图上的文字重算，能复现出同一个码；谁改过字，码就不对了 | 这张照片**确实是**这台设备在某个时刻拍的 |

后者的原因是校验方没有留底：任何人拿到这些字段都能自己算出同一个码。
真正「可验证」需要服务端在拍摄时留一份摘要存档 —— 那是下一步的事。
在这之前，本地算的这个码是**把这件事提前准备好**，而不是假装已经做到了。
设置页的说明文字只写它能证的，不写它不能证的。

**为什么单独占一段**：试过让它和左侧的地点/备注挤在同一条水平带上（更接近参考图的观感），
但左侧最长那行是地点（42f 粗体）、长备注能到 25 字以上，窄屏上必然撞车 ——
要么给左侧缩字号（伤主体信息），要么把品牌缩到看不清。垂直分开后两边各自完整，
且零碰撞，代价只是品牌行比左侧文字低一点点。

### 3.10 内置占位 Logo：一份手写的矢量稿

原来没选 Logo 时，卡片右侧永远是空的（回落成单位文字）。但**绝大多数人不会**
为了打个卡先去相册翻一张自己的 logo 出来 —— 所以现在内置了一份**中性占位稿**，
默认就开，装上就带。规则是：

```
用户自选图片  >  内置占位 Logo  >  都没有（卡片右侧回落成单位文字）
```

三个地方查这套优先级 —— 主界面预览、按下快门出图、设置页预览 ——
都走同一个 `LogoStore.pick()`。分开写的话就会出现「设置页看着有、拍出来没有」
这种最难查的不一致。

设置页底下会明写**当前用的是哪一个**（`当前使用：内置占位 Logo` / `自定义图片` /
`不使用 Logo（卡片右侧显示单位文字）`），否则用户分不清是内置生效了还是压根没设上。

**它长什么样**：中性灰蓝（`#3E4C59`）圆角方块 + 白色（`#FFFFFF`）快门环，340×275，
**不含任何公司标识**。选"相机"这个通用意象而不是某个牌子是有意的 ——
内置的只要不丑、不空着就够，谁真要用自己的图，在设置页选一张即覆盖。

**为什么是矢量而不是塞张 PNG**：这份图形是手写的 path，矢量形式只占 **0.5KB**，
而水印画到 1440 宽都不会糊；换成位图要么放大后糊，要么得塞一张大 PNG 把包撑起来。
（`verify/trace_logo.js` 那套"位图 → 矢量"的描摹管线仍然留着 —— 想把自己的位图
logo 描成矢量稿时它能用；但当前内置的这份没走它，是直接手写的。）

同一份稿子要出现在三个地方，任何一处漂了都会表现为「网页版有、安卓没」：

| 位置 | 形式 |
|---|---|
| `watermark-camera/assets/logo-placeholder.svg` | 真源（手写） |
| `watermark-camera/index.html` 的 `BUILTIN_LOGO_SVG` | 网页版内联（单文件可用，不能 fetch） |
| `app/src/main/res/drawable/logo_placeholder.xml` | 安卓 VectorDrawable |

改了图形之后要重跑：

```bash
node verify/inject_logo.js index.html assets/logo-placeholder.svg   # 注入网页版内联
node verify/logo-parity.js gen ../watermark-camera                   # 三处静态比对 + 出探针页
# 再用 Chrome --dump-dom 跑探针页，把结果喂回 check（Node 里 spawn Chrome 会 EBUSY）
```

`verify/logo-parity.js` 静态比对三处：pathData **逐字**相同、viewport 与 viewBox 一致、
填充色与描边色逐条对应、`fill-rule=evenodd → android:fillType="evenOdd"`。
描边那条是新加的 —— 快门环整条都是 `stroke` 画出来的，只比 `fillColor` 等于没比。
之后它还会让 Chrome 真把矢量画到 canvas 上数像素（灰蓝主体、白色快门环、保留透明底）——
矢量"资源在、但画不出来"只有真渲才知道。

**注意**：水印整幅是画在软件 `Canvas` 上的，所以安卓端把 VectorDrawable
**栅格化**成 Bitmap 再用。这里有个坑：别拿 `drawable.intrinsicWidth` 当像素宽，
它带 density 缩放（340dp 在 3× 屏上是 1020px），只拿它算宽高比。

### 3.11 底部对齐：左下正文块与右下品牌区共用一条底边

原来品牌区被摆在正文块的**下方**（`y = 正文块底 + 间隙`），于是「防伪 …」那行比
「2026.09.27 星期日」低一截 —— 看着就是没对齐，用户第一眼就指出来了。

现在底部模式**以 `h - pad` 为共同基线**，两块各自按自己的高度往上让：

```
正文块  [1745.97, 1885.33]     ← h - pad = 1920 - 34.67 = 1885.33
品牌区  [1724.17, 1885.33]     ← 底边严格相等
卡片    [1532.17, 1686.83]     ← 在两者之上，间隔 = GAP_CARD 28s
```

代价是两块**落在同一条水平带上**了，于是长地名会直接压到品牌名上 ——
所以正文行多了两条宽度上界（见 3.5），这是同一件事的两半，改一半都不行。

**框对齐 ≠ 看着齐**：上面量的是布局框底边。两块字号不同、descent 也不同，
所以字形的**墨迹**底边还会差一点。用 `verify/ink_align.py` 在渲染图上直接数行号：

```bash
python verify/ink_align.py app/build/test-render/A-bottom-text-unit.png
# 正文块最后一行墨迹下沿 = 1874
# 品牌区最后一行墨迹下沿 = 1875
# → 差 +1 px（竖屏；品牌区字号放大到 40 基准后从 +5 收窄到 +1）
```

这 1px 是字体度量差异（两块字号不同、descent 也不同），不是算错位置 ——
想要"绝对齐"只能让两块用同一个字号，那层级就没了。

### 3.12 水印上点一下就改：地点 / 日期时间（弹出式）

水印上的地点和时间**本身就是入口**，不用先去顶栏找按钮：

| 点哪里 | 开什么 | 改什么 |
|---|---|---|
| 地点那行 | 地点编辑器 | 手输 / 常用地点下拉 / 用定位反查（和顶栏胶囊同一个弹窗） |
| 日期行，或卡片里那串时间大字 | 日期时间滚轮 | 上排年/月/日，下排时/分/秒 |

滚轮那套用 `NumberPicker`，**一屏六条**：系统只有 `DatePickerDialog` 和
`TimePickerDialog` 两个分开的窗，改一个"日期对、时间也对"的组合要过两道窗点两次确定。
（设置页里那份两步走的入口保留着 —— 它给"顺手改一下"用，不必拨滚轮。）

细节上做对了几件容易漏的事：

- **命中区比看到的放大一圈**（`HIT_SLACK = 12` 基准像素，1440 宽下 16px）。
  小字号下手指差十几个像素太正常，点不中只会让人以为"这功能没有"。
- **只有命中才吃事件**：没命中时 `onTouchEvent` 直接返回 `false`，
  这一下继续落到预览区做点屏对焦 —— 浮层把它吃掉的话预览区就"死"了。
- **按住会亮一层半透明底**（`HIGHLIGHT_BG`）。水印上没有按钮，
  不给反馈就没人知道这里能点。它只出现在预览里：出图走 `ImageWatermarker`，
  那条路不传 `highlight`。
- **点空白处、点品牌区都不响应**。品牌区特意不做入口 —— 用户想点品牌名时
  弹出一个跟品牌无关的编辑器，比不响应更糟。
- **月份/日期/时分秒补零成两位**，否则滚轮里 `9` 和 `12` 混排看着是歪的。
- **改年月会重算当月最大天数**并把日往回拉：否则滚轮能停在「2 月 30 日」上，
  而 `Calendar` 会静默进位到 3 月 2 日 —— 用户看到的和印出来的不是一个日期。
- **滚轮的软键盘被关掉**（`FOCUS_BLOCK_DESCENDANTS`）：滚轮本来就是拨的，
  点一下弹出输入键盘会把整张卡顶上去，还得先收键盘才能接着拨。

弹窗壳是 `CardPopup`（遮罩 + 居中圆角卡 + 标题 + 内容 + 右下角按钮排），
不是 `MaterialAlertDialogBuilder`，原因见 `CardPopup.kt`：两个编辑器要长得一模一样、
按钮要放得下三个、还要点遮罩关闭。

配色上有个**必须写死**的地方：卡片永远是浅底深字，因为它永远压在深色的相机预览上。
所以弹出层单独一套 `Theme.WatermarkCamera.Popup`（**Light**，不跟 App 的 `DayNight` 走）——
跟主题走的话，深色模式会得到"浅底 + 白字"，`NumberPicker` 的滚轮字直接看不见。

键盘还自己躲：`windowSoftInputMode` 那条 `SOFT_INPUT_ADJUST_RESIZE` 在 API 30 起废弃、
本工程又开了 edge-to-edge，API 35 上直接不生效（键盘盖住卡片下半截，「完成」都按不到），
所以改成自己听 IME 的 inset 加在根节点下内边距上（`CardPopup.avoidIme()`）。

### 3.13 边距：一处收窄，三边同时动

`PAD` **一个值管三边** —— 左边正文块的起点、右边品牌区的终点、以及整个下方块的
基线（`h - pad`）。所以「左右再靠边一点」和「再靠下一点」是同一件事，
不是两次改动。

```
PAD  40 → 26（1080 基准）          1440 宽下：53.33 → 34.67
正文块底边     1866.67 → 1885.33   （下移 18.67）
品牌区右边界   1386.67 → 1405.33   （右移 18.67）
```

**不拆成"左右一个、下方一个"**：那就会出现"左右收窄了、底边还在老位置"这种半吊子
状态，而且以后每次改版式都得记住两个数之间是什么关系。

原来那个 40 是照网页版定的，但网页版是**看**的（图片周围本来就有浏览器留白），
相机是**拍**的 —— 成图四周没有留白可言，水印该像官方水印那样压到边上去一点。

连带放松了一条上界：内容区从 `w - 2*40s` 变成 `w - 2*26s`，
所以条幅宽度上限从 1333.33 变成 **1370.67**（时间条实际只有 763.67，够用）。

`PAD` 是 `internal` 而不是 `private`：单测要按同一个数算期望值 ——
测试里写死一份 `40f` 的话，改了这里它不会报错，只会悄悄量错东西。

## 四、实现要点

- **所见即所得**：预览浮层和出图共用同一个 `WatermarkRenderer`，所有尺寸按
  `s = 画面短边 / 1080` 归一化 —— 预览里水印在什么位置，照片里就在什么位置。
  取**短边**而不是宽度：竖屏时短边就是宽度（与旧版逐像素一致），横屏时若按宽度算，
  水印会被放大近 40%。
- **几何只量一次，绘制 / 命中判定 / 单测共用**（`WatermarkRenderer.measure()` + `place()`）。
  原先 `draw()` 自己量一遍、`drawCard()` 内部又量一遍 —— 两处入参一漂，
  "画出来的卡片"和"测试断言的卡片"就不是同一个东西，而两者看上去都"对"。
  现在 [量] 与 [摆] 各自只有一个实现，`draw` / `hitTest` / `layoutMetrics` 全部走它，
  于是"改了算式不会只改到一半"是结构保证的，不靠纪律。
- **横屏几何换算独立成 `PreviewGeometry`**：传感器吐出的分辨率永远是横向的
  （如 1440x1080），屏幕上显示成 3:4 还是 4:3 由设备方向决定。
  这块是纯函数、有单测，并有「按旧逻辑会算错」的回归护栏 ——
  横屏最容易踩的坑就是拿竖屏比例去横屏容器里算内接矩形，结果浮层变成画面中间一根竖条。
- **无 Google 依赖**：定位走系统 `LocationManager`，反查地名走系统 `Geocoder`。
  不需要 Google Play 服务，国内手机直接用。
- **不联网**：实测 `aapt2 dump badging` 出来的权限表里**没有 `android.permission.INTERNET`** ——
  这个包在系统层面就发不出网络请求。权限是相机、定位、Android 10 以下用的存储写，
  外加一条 `ACCESS_NETWORK_STATE`。
  这条不是我们申请的，是 `androidx.core` / `androidx.lifecycle-process` 的 manifest 合并带进来的
  （`manifest-merger-debug-report.txt` 可查证），只用来读网络状态，**读网络状态 ≠ 能联网**。
  核实命令：`aapt2 dump badging <apk> | grep -c INTERNET` → `0`。
- **拍照流程**：CameraX `ImageCapture` → 按 `rotationDegrees` 转正 → 画水印 → 存 MediaStore。
  存完后图片以 4:3 落在相册里。
- **旋转靠 `configChanges` + 手动更新相机方向**：声明了 `orientation|screenSize` 让 Activity
  不重建（重开会闪一下、状态全丢），代价是没人帮我们更新相机 —— 所以
  `onConfigurationChanged` 里显式把 `Preview`/`ImageCapture` 的 `targetRotation`
  同步成当前屏幕旋转，否则横屏拍出来的照片是横躺的。

## 五、怎么验的（不是"应该能跑"）

编译通过 ≠ 画得对，也 ≠ 逻辑对。所以有 **104 个测试**，跑在两种 runner 上：

```bash
./gradlew testDebugUnitTest
# 产物: app/build/test-render/*.png
```

分两类是**故意的**：

| 类型 | runner | 例子 | 一轮耗时 |
|---|---|---|---|
| 碰 `android.graphics` 的 | Robolectric + NATIVE | 版式渲染、Logo 真渲、布局量坐标 | 5~13 分钟 |
| 纯字符串 / 纯算法的 | 普通 JUnit | `AddrTest`、`BrandMarkPathsTest` | 秒级 |

理由很实在：解析器、排版算式这类东西改一行就要验一次，塞进 Robolectric
会让每次迭代都等十几分钟 —— 本轮就吃过这个亏（路径解析器出问题时，
要等一整个 Robolectric 类跑完才知道错在哪）。

**二、文案与版式断言 —— 数字，看图看不出来**

小数点位数、单位、行数这类东西渲成图根本分辨不出来，所以直接断言字符串：

```
水印文案 = [星海市云山区·风和苑, 2026.09.27 星期日, 30.2741°N  120.1551°E, ±8m  海拔12m]

水印文案 = [星海市云山区·风和苑, 2026.09.27 星期日, 备注 设备运行正常, 打卡人 张三]
品牌区文案 = [今日水印, 相机真实可验, 防伪 5H3HXQ9UL72SS9]
```

同时断言"旧的长写法不该再出现"（`定位精度`、` 米`）与"`打卡人：` 不该再拼进正文"，
防止以后改回去。

条幅宽度同样是数字断言（`cardMetrics` 返回 `[卡片宽, 画面宽, 边距, 时间字号]`），
比盯着 PNG 目测靠得住：

```
纯打卡条宽=519.67  带Logo条宽=842.87  上限=1370.67  占满宽比例=61.5%   ← 没撑满
超长内容 条宽=1370.67  上限=1370.67  时间字号=37.3                    ← 缩字号而非溢出
品牌区宽=319.0  右边界=1405.33  画布宽=1440.0  边距=34.67             ← 贴右下角且没溢出
```

**二之一、底边对齐 / 宽度上界 / 命中区 / 按下反馈 —— 全是数字**

`layoutMetrics` 一次返回 12 个边界值，`lineWidths` / `lineHitPoints` / `cardTimeHitPoint`
把渲染器**认的那些矩形**原样拿出来：

```
正文块 [1745.97, 1885.33]  品牌区 [1724.17, 1885.33]  卡片 [1532.17, 1686.83]
时间条宽=763.67  行宽上界=763.67  逐行宽=[521.0, 398.0]  品牌区左边界=1086.33
行命中点 = [[295.17, 1783.49, 1], [233.67, 1853.17, 2]]   ← 第三个数是行用途标记（1=地点 2=日期）
卡片时间命中点 = [393.17, 1609.50] → DATETIME
[长地名] 正文底=1885.33 品牌底=1885.33    ← 底边对齐在长地名/无卡片/带坐标下同样成立
```

`lineHitPoints` 故意**让渲染器给点**，而不是让测试自己算 `pad + 字号×字数/2`：
自己算的话，量的就不是渲染器判的那块矩形，命中断言会退化成"我算的点在我算的框里"，恒真。

按下反馈靠**两张图的像素差异**判定 —— 半透明的底压在渐变遮罩上，
肉眼看不出"亮了一点"和"没亮"，但差异包围盒能，而且能顺便证明它没糊到品牌区：

```
地点行按下：差异像素=39580  包围盒=(26, 1738)-(563, 1828)      ← 右边界 563 < 品牌区左边界 1086.33
卡片时间按下：差异像素=71355  包围盒=(26, 1524)-(535, 1893)
```

第二条的包围盒是**两块并集**：正文里的日期行和卡片里的时间大字是同一个值
（都归 `TapTarget.DATETIME`），点一下会同时亮两处 —— 这是有意的，它们改的本来就是同一个东西。
所以断言写成"上沿不高于卡片上沿、下沿不超过正文块下沿"，而不是"等于卡片那一块"，
免得下一个人把它当成 bug 修掉。

**二之二、矢量品牌稿 —— 数据 6 例纯 JVM + 渲染 6 例真渲**

「今日水印 / 相机真实可验」走的是**轮廓路径**（见前面 §3.9），所以验的对象分三层：

**层一：路径数据本身**（`BrandMarkPathsTest`，普通 JVM，秒级）——
字形数、命令与操作数的配比、轮廓点数、坐标范围、字符集。
这层刻意不碰 `android.graphics`：数据写坏了当场就能发现，
不必等 Robolectric 那十几分钟。

**层二：真渲出来数像素**（`WatermarkRendererTest`）——
灰块的**精确色**像素数、以及块内**深字精确色**像素数：

```
灰块纯色 ≈ 3010 px，范围 x 1245..1404  y 1797..1838   ← 宽 160 ≈ 预期 160.8
块内深字纯色 ≈ 2340 px                                ← 覆盖率 34.8%，汉字典型值
```

这里**必须用精确色，不能用宽容差**。宽容差会把白字的抗锯齿边缘也算进来
（纯白到纯黑的中性渐变必然穿过浅灰区间），后果是两条断言一起失效：
块范围被撑大（实测 x 从 1207 起，而块真正的左边界在 1266）、
"块内深色像素"混进大片黑色背景（实测 7507 里 5625 是背景）。
数字都很好看，**但一个字不画它也会通过** —— 等于没写。

深字色是带蓝调的 `(38,43,51)`，而白字边缘只能产生灰度（R=G=B），凑不出这个值，
所以这份计数天然不会被白字污染。

**层三：提取器本身的闭环**（`verify/glyph_parity.js`）——
不比字，比像素：把提取出的路径画进 canvas，再把同字体的 `fillText` 画一遍，逐像素相减。
`今日水印` 差 408/1602220 = **0.025%**，`相机真实可验` 差 222/3003890 = **0.007%**，
差异全落在抗锯齿边缘。这层证明的是「提取器没把轮廓读歪」，
与「版式好不好看」是两件事，别混为一谈。

**三、Logo 存取链路 + 内置 Logo —— 13 例**

用 `ShadowContentResolver` 注册自定义流，把「只开一次流」这件事钉死：

```
保存结果: Ok(width=400, height=267), openCount=1      ← 同一个 URI 只被打开了一次
一次性流保存结果: Ok(width=400, height=280)            ← 只能打开一次的 provider 也能存
失败原因: 打不开这个文件 / 这个格式解不了（试试 PNG / JPG）/ 文件是空的
```

内置 Logo 那条链路是**真的把矢量画出来再数像素** —— 「资源在、但画不出来」
（矢量不受支持、比例算错、画成空白）只有真渲才能发现：

```
内置 Logo 尺寸: 400×324                                ← 保持参考图 340:275 的比例
内置 Logo 像素占比: 绿=21.66% 橙=0.90%                 ← 绿主体 + 橙点缀，不是空白
选Logo的优先级: 自选 > 内置 > 无（关掉内置且无自选 → null，回落成单位文字）
内置Logo开关能存能读
```

**六、顶栏不溢出 —— 4 例真量坐标**

`TopBarLayoutTest` 把界面按 360dp / 320dp 两种屏宽真的 inflate + measure/layout 一遍，
读四个控件的 `right` 边界，断言设置按钮的右边界不出栏 —— 这是"地点太长把 ⚙ 挤出屏幕"
那个 bug 的回归护栏（地点胶囊已经是 `0dp + weight=1`，不再靠 `maxWidth` 硬顶）：

```

栏宽=640 地点右=354 张数右=428 闪光右=520 设置右=612   ← 320dp 窄屏也放得下
```

**七、防伪码 —— 7 例，含跨实现一致性**

防伪码这种东西最容易"看起来像码就行"，所以断言分成四层：

```
格式     防伪码 = 5H3HXQ9UL72SS9              ← 14 位连排，无分隔横线
字符集   不含 0 / O / 1 / I                   ← 数字字母混排时这四个几乎必抄错
确定性   同输入必同码；改备注/地点/机型就变
稳定性   同一分钟内码不变                      ← 只算到分钟，否则预览与出图的码会不一致
```

**跨实现一致性**是这里最硬的一关：安卓用 `MessageDigest`，网页版是手写的**同步** SHA-256
（`crypto.subtle.digest` 是异步的，没法在每帧渲染里用）。两边独立实现，用同一组输入对拍 ——
网页版算出来的码必须和安卓单测真实跑出来的码**逐字符相同**：

```bash
node verify_brand_parity.js
# SHA-256 长度 55/56/64/119/120/1000B 与 Node crypto 一致   ← 换块边界，补位就错在这附近
# 与安卓版同码 base() + 定位 → 5H3HXQ9UL72SS9
# 与安卓版同码 base() 无定位 → 2SA9N5GMUT7L5R
```

用别人（Node crypto / JDK）的实现当基准，而不是拿自己另一份 JS 自我验证 —— 后者
只是把同一个错误抄了两遍。

> **改基准数据的成本**：种子串里含**地点、备注、打卡人、单位、机型、经纬度**，
> 所以动其中任何一个，上面这两个基准值都会变，`verify_brand_parity.js` 里的
> `want:` 也要跟着换。别把码抄到图上 —— 图上是渲染结果，字号一改就可能被抗锯齿吃掉一位。
> （最近一次就是因为把示例单位名和地名整体换掉，两个值从 `XP6RKVXVBTSQ7M` /
> `XQKXGKJ6Q9Y7TR` 变成了现在这两个。）

**八、内置 Logo 三处一致 —— 静态比对 + 浏览器真渲**

同一份矢量稿要同时存在于三处（真源 SVG / 网页版内联 / 安卓 VectorDrawable），
任何一处漂了都会表现为「网页版有、安卓没」。`verify/logo-parity.js` 分两段查：

```
静态  内联 SVG 与 assets/logo-placeholder.svg 一致
      每条 pathData 逐字相同（换图形时两边各改一半，画出来就是废的）
      viewport 与 viewBox 一致（2720x2200）、viewBox 原点为 0,0
      填充色一致 ["#3E4C59","#FFFFFF"]
      描边色/宽度一致（#FFFFFF / 140）        ← 快门环整条都是描边画的，漏了这条等于没比
      fill-rule=evenodd 已转成 android:fillType="evenOdd"

浏览器  默认(无自选) → 用内置 Logo / 有自选 → 自选优先 / 内置关掉且无自选 → 回落成单位文字
        natural = 340x275        ← 只给 viewBox 时 canvas 画不出（要给 width/height）
        canvas  = 400x324
        灰蓝主体 59.61%  白色快门环 8.00%  不透明 68.0%（保留透明底）
```

安卓端同一张图数出来是 **灰蓝 59.61% / 白 8.01%**，与浏览器的 59.61% / 8.00% 几乎逐位相同 ——
两端各自栅格化，像素占比这种粗指标能对到小数点后就说明画的是同一张。

| 自动反查地名 | **未上真机** | 依赖系统 Geocoder，部分 ROM 无服务 |
| 横屏取景与出图 | 渲染已验证 | 几何有单测；真机横拍未验 |

## 七、已知限制

- **最低 Android 8.0（API 26）**。Android 10 以下走旧存储路径，需要「存储」权限。
- **用户自选的 Logo 支持 PNG / JPG / WEBP / HEIC**（HEIC 走 `ImageDecoder`，需要 Android 9+）；
  不支持 **SVG**（它是矢量格式，不是位图）和超过 **24MB** 的原图。
  选不上时提示会写明具体原因，不会只说"失败"。
  内置的那份占位 Logo 反而是矢量（编译进包里的 VectorDrawable，用之前才栅格化）——
  这是刻意的不对称：用户从相册里选的只可能是位图，而内置的那份我们自己能挑格式。
- **反查地名依赖系统 Geocoder**。部分设备/ROM 没有地理编码服务，会提示「没查到」——
  此时手填即可，应用不会编一个看起来对的地名。
- **超长地名的下限是名义字号的 45%**。29 字的地名缩到 47.6% 刚好放得进时间条；
  再长（比如 60 个字），45% 的下限就兜不住了，那一行会越过上界、压到品牌区。
  要彻底解决得**折行**（把地名拆成两行，正文块变高、品牌区跟着往上让），
  这会改变行数从而动到所有基准值，本轮没做 —— 真遇到了再说。
- **日期时间弹窗的滚轮只改到秒**，没有「昨天/明天」这种快捷档，
  也不改时间格式之外的显示样式（`时间格式` 按钮切的是"含秒 / 不含秒"两档，
  对应已有的 `showSec`；不是任意格式串）。
- **弹出卡片是浅色的、不跟深色模式**。它永远压在深色的相机预览上，
  跟着 `DayNight` 走会在深色模式下变成白纸白字。这是刻意写死的，不是漏了适配。
- **横屏的几何与渲染已验证，但相机取流没上真机跑过**。旋转时相机方向、横屏取景、
  权限弹窗这几条只在代码层面正确。装了之后横屏拍一张，如果水印位置不对或照片躺倒，
  把现象发我。
- 水印**不防篡改**（照片是普通 JPEG，可以 P）。右下角的防伪码只能证明
  「水印字段自洽」（拿图上的文字能重算出同一个码），**不能证明照片是这台设备拍的** ——
  要防篡改得在服务端留摘要做校验，这是下一步的事。别把它当"验真"用。

## 八、和 Web 版的关系

> **状态：网页版已冻结，只做安卓。**
> 下面的对齐关系仍然成立，但**改动只往安卓走**，不再同步回网页版。
> 网页版留着的价值是充当**第二套独立实现** —— 防伪码（手写同步 SHA-256 vs
> JDK `MessageDigest`）和地址精简靠它交叉验证，这是单靠自己跟自己对拍换不来的。
>
> 唯一一次例外：品牌区第三行的标签从「防伪码」改成「防伪」时，网页版**也改了这一个字符串**。
> 它画在同一套版式上，两边文案不一致会让以后的对拍图对不上；一个字符串的同步成本是零，
> 不算"重新做网页版"。

同目录上级的 `watermark-camera/index.html` 是同一个水印版式的单文件网页版，
两者的水印参数是逐条对齐的（`WatermarkRenderer.kt` ↔ `drawWatermark()` / `drawCard()`），
地点精简也是（`Addr.kt` ↔ `compactAddr()`，用 `verify_addr_parity.js` 对拍，21 条用例一致），
防伪码同样（`AntiFake.kt` ↔ `antiFakeCode()`，用 `verify_brand_parity.js` 对拍，
网页版那个手写 SHA-256 与 Node crypto 逐字节一致、算出的码与安卓版逐字符相同）。
内置 Logo 是同一个来源（`LogoStore` ↔ `logoSrc()` / `BUILTIN_LOGO_SVG`，
用 `verify/logo-parity.js` 查三处一致 + 浏览器真渲数像素）。

**两处差异**（都是刻意的）：

| | 安卓 | 网页 |
|---|---|---|
| 归一化基准 | 短边 `s = min(W,H)/1080` | 宽度 `s = W/1080` |
| 防伪码里的机型 | `Build.MODEL` | 空 —— 浏览器拿不到可靠机型 |

第一处：竖屏出图两者完全一致，只有横屏出图时网页版会把水印放大。网页版是竖屏取景优先，不打算改。
第二处：网页版算出的防伪码因此在**真机运行时**与安卓版不同 —— 这本身没问题（它俩本来就是不同设备）。
注意 §五 那两组对拍码之所以能相同，是因为**对拍时两边都把 `deviceTag` 置空**；
别拿真机上的码跨端比对。

改水印样式**只需改安卓**。三个对拍脚本各自会红 —— 它们拿网页版当"另一套独立实现"，
安卓这边参数一变而网页版没跟着变，脚本立刻报不一致。那时有两条路：同步网页版，
或者接受差异并改脚本里的期望值（**后者必须在脚本里写清为什么**，否则下一个人会当成 bug 修）。
