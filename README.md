# 打卡水印相机 (Android)

拍照时把 **地点 / 日期 / 时间 / 单位 Logo** 烙进照片里的原生 Android 应用。
水印版式参考「今日水印相机」：黄色「打卡」标签 + 大号时间的白色卡片，下方跟地点与日期。

白卡片**宽度按内容自适应**（约半屏宽），不是一条从左通到右的长横幅 —— 见 3.5。

**默认不含经纬度**（经纬度、定位精度、海拔有开关，收在「高级」里，默认全关）。

## 一、在 GitHub 上编译（不用装 Android SDK）

1. 新建一个仓库，把本目录所有文件推上去（`.github/` 也要推，否则不会触发构建）：

   ```bash
   git init
   git add .
   git commit -m "打卡水印相机"
   git branch -M main
   git remote add origin https://github.com/<你的用户名>/<仓库名>.git
   git push -u origin main
   ```

2. 推送后自动开始编译。到仓库页面的 **Actions** 标签看进度，第一次大约 3~5 分钟
   （实测 **2 分 57 秒**）。CI 里有两道防线（「守卫」与「编译环境自检」），
   环境问题会在**有名字的步骤**上失败，而不是甩一句看不懂的 setup-gradle 报错 ——
   见第二节末尾。**失败用时 20~30 秒 = 死在环境阶段，跟代码无关**，别去翻 Kotlin。

3. 编译成功后，点进那次运行，页面底部 **Artifacts** 里下载：
   - `watermark-camera-debug` —— 调试包
   - `watermark-camera-release` —— 正式包

   下载下来是 zip，解压出 `.apk`，传到手机上点一下就能装。
   （手机需要允许「安装未知来源应用」。）

   也可以手动触发：Actions → 构建 APK → Run workflow。

> **拿包别去 Artifacts，去 Releases。** 推 main 之后 CI 会自动刷新一个
> **「最新构建（main 自动构建）」** 预发布版 —— **点开就能下、不用登录**，
> 而且**每次推 main 都会覆盖成最新的一份**（见 1.2）。
> Artifacts 只当备份用：它**要登录 GitHub 才能下**（公开仓库也一样），
> 而且默认 **90 天后过期**。
>
> 想要"下载下来就永远是这个包"的稳定版本，才需要打标签，见 1.2。

> 两个包都用 debug 签名，都能直接安装。要上应用商店的话，把 `app/build.gradle.kts`
> 里 `signingConfig = signingConfigs.getByName("debug")` 换成你自己的 keystore。

### 1.1 CI 里 action 的版本号怎么定（Node 20 弃用警告）

GitHub 会对仍运行在 Node 20 上的 action 给出警告注解（Annotations 区那两条），并**强行**
把它们塞到 Node 24 上跑。清掉之后要防止它回来，**靠读版本号是读不出来的** ——
`v4 → v5` 这种「顺手升一档」不一定管用：每个仓库把 node24 放在哪一版是**各自决定的**。

下表是 2026-09-28 逐个读各 tag 的 `action.yml` 里 `runs.using` 得到的，不是凭印象：

| action | node20 止于 | 首个 node24 |
|---|---|---|
| `actions/checkout` | v4 | **v5** |
| `actions/setup-java` | v4 | **v5** |
| `actions/upload-artifact` | **v5**（不是 v4） | **v6** |
| `gradle/actions`（setup-gradle） | v4 | **v5** |

三件事值得记住：

1. **`upload-artifact` 的 node20 一直延续到 v5。** v5 只是"预先支持" node24，默认仍跑
   node20，所以写 `@v5` **照样报警告**，必须 v6。好消息是 v6 的 inputs 与 v4 完全一致
   （`name` / `path` / `if-no-files-found`），属于纯运行时升级。
2. **不要无脑升到 latest。** `gradle/actions@v6` 把缓存拆成了专有组件
   `gradle-actions-caching`，升上去等于接受 Gradle 商业条款 —— 而 `setup-gradle` 的缓存
   **默认就是开着的**。我们只需要清掉弃用警告，不必顺带接受一份许可。
   （`setup-java@v6` 同理无必要：它改了 Zulu 的发现方式与 `jdkFile` 的命名。）
3. node24 的 action 要求 Actions Runner ≥ **2.327.1**。GitHub 托管 runner 总是满足这一点；
   只有将来换成自建 runner 时才需要注意。

核对方式 —— **用真实的 `action.yml` 说话**：

```bash
python verify/ci_action_versions.py .
# 读每个 uses 指向的 ref 的 action.yml，取 runs.using；
# 出现 node20 就退出码 1，并把「该升到哪一版」直接打出来。
```

**故意没把这个脚本挂进 CI**：它要联网拉 `raw.githubusercontent.com`，一抖动就会让 CI
因为无关原因变红 —— 这跟 `lintVitalRelease` 是同一类问题（不动产物、只添噪音）。
放在 `verify/` 里手动跑，或者在升级 action 之前跑一遍。

### 1.2 把 APK 放进 Release

**两条轨道，互不干扰**：

| 触发 | 发到哪 | 资产会不会变 | 什么时候用 |
|---|---|---|---|
| 推 `main` | `latest` 下的**「最新构建（main 自动构建）」**，预发布 | 每次推送**整个覆盖** | 平时要看/装**最新**的包，看这个（见 1.3） |
| 推 `v*` 标签 | 版本 Release：`v1.0`、`v1.1`… | **不会变** | 要发一个**确定的版本**（下面这段） |

> 2026-09-28 定下这条分工。之前只有标签那一条轨道，于是"main 上早就修好了、
> Release 里还是旧包"—— 要拿最新包只能去 Actions 下 Artifacts（要登录、90 天过期），
> 或者临时打个标签。连着被绊了两次才把这条补上。

**发一个确定的版本**：在维护者机器上敲**两条命令**，APK 就会出现在
`https://github.com/<owner>/<repo>/releases` —— 那里**不登录也能下载**，也不会 90 天过期：

```bash
git tag -a v1.0 -m "第一个版本"      # 版本号跟 app/build.gradle.kts 里的 versionName 对齐
git push origin v1.0
```

> **如果 `git push` 卡住、一个字节都不传** —— 大概率是凭据助手在等交互，不是网络。
> 本机的 `credential.helper` 是**多值**的，第一个 `helper-selector` 会阻塞。
> 绕过它：`git -c credential.helper= -c credential.helper=manager push origin v1.0`
> （排查全过程见技能 `git-push-hang-diagnose`。2026-09-28 为此白等过 18 分钟。）

**为什么推标签会触发构建**：`on.push` 里 `branches` 和 `tags` 是**同时**定义的。官方文档
原话是"只定义 `tags` 或只定义 `branches` 时，工作流不会对未定义的那一类 ref 运行" ——
所以只写 `branches` 时推标签**什么都不会发生**（这就是加上 `tags: ['v*']` 的原因），
而两者都写时两类 ref 都会触发。标签**必须以 `v` 开头**（`v1.0`、`v2.1.3`）；
写成 `1.0` 不会发布，因为条件就是 `startsWith(github.ref, 'refs/tags/v')`。

推标签后跑的是**同一次运行的最后一个步骤**「发布到 Releases（仅推 v\* 标签时）」：
它把刚编好的两个包用 `gh release create` 挂上去。四个设计点：

1. **权限**：job 上显式写了 `permissions: contents: write`。别指望 token 默认能写 ——
   仓库设置会把它降成只读，那时报的是 `HTTP 403: Resource not accessible by integration`，
   从字面上完全看不出是"权限"问题。
2. **幂等**：`gh release create` **没有 `--clobber` 参数**（只有 `gh release upload` 有），
   所以"版本已存在"时 create 会直接失败。脚本先 `gh release view` 探一下：
   已存在就走 `gh release upload --clobber` + `gh release edit`。这样两种情况都不会红：
   ① 同一个标签重跑 workflow；② 你先在网页上建过空 release。
3. **`--verify-tag`**：只在远端确实有这个 tag 时才建。不加的话，gh 会拿**默认分支**自动
   造一个同名 tag —— 那等于把版本号悄悄指到一个错的提交上。
4. **资产命名**：文件名用 ASCII 且带版本（`watermark-camera-1.0-release.apk`），
   页面上的下载名、`curl`/`wget` 的命令行都干净，多版本之间也不互相覆盖；
   中文放进「显示标签」（文件名后面跟 `#标签`），页面上照样是中文。

**没用第三方 action**（`softprops/action-gh-release` 之类）的原因：`gh` 是 GitHub 托管
runner 的预装工具，少一个要审计 Node 运行时的依赖 —— 刚为了清掉 Node 20 注解逐版读过
各 action 的 `action.yml`（见 1.1），不想再引进来一个。自检步骤里会打印 `gh --version`，
万一哪天 runner 镜像变了，日志当场就能看到。

**核对发布结果**（公开仓库免鉴权可读）：

```bash
curl -s https://api.github.com/repos/<owner>/<repo>/releases \
  | python -c "import json,sys; [print(r['tag_name'], r['draft'], [a['name'] for a in r['assets']]) for r in json.load(sys.stdin)]"
```

> **查"这次运行"时有个坑**：workflow runs 列表接口里，**标签触发的运行不在 `ref` 字段上**
> （那里返回 `null`），要看 `head_branch` —— 它的值就是标签名（`v1.0`）。按
> `ref == 'refs/tags/v1.0'` 去匹配会**永远匹配不上**，看起来像"标签根本没触发构建"。
> 另外未鉴权的 API 只有 **60 次/小时**，用脚本每 20 秒轮询几次就耗尽了；而**耗尽后
> 返回的是错误 JSON，很容易被自己的解析脚本当成"没有这次运行"**。这两个叠在一起，
> 2026-09-28 让我误判过一轮"标签没触发"。加上 `-H "Authorization: Bearer <token>"`
> 是 5000 次/小时，够用一天。

**想撤回**：

```bash
gh release delete v1.0 -y                    # 只删 Release，保留 tag
gh release delete v1.0 -y --cleanup-tag       # 连 tag 一起删（之后可以重新打）
```

**不想敲命令也行**：网页上 Releases → *Draft a new release* → 选/建标签 → 拖入 APK
（从 Actions 的 Artifacts 解压出来）→ Publish。只是这样就每次都得手动拖，
而 `git push origin v1.0` 是自动的。

**实测（2026-09-28，v1.0 首次发布）**：

```text
推标签 → 63 秒完成（03:47:10 → 03:48:13，success）
      （同一时刻 main 分支那次运行只刷新「最新构建」，不发版本 Release —— 见 1.3）
匿名下载（刻意不带 Authorization 头）  http=200  一次成功
      release 8 696 313 B / debug 10 913 851 B
      下载回来的 MD5 与 Release 说明里写的逐字符一致
         debug   ca558d28f299921f30b55e6cb5a55b26
         release 74718a1cdb537bf202f63cd734c3433a
包本身 → verify/apk_content_check.py 全部通过
与上一版 CI 产物逐条目 CRC 比对：
```

### 1.3 main 每次推送刷新「最新构建」（2026-09-28 新增）

**症状**：CI 绿了、Actions 里也有包，但 Releases 页面上还是老版本。原因是发版只挂在
标签上，`git push origin main` 压根不碰 Release —— 要拿最新包就得先打标签，
或者去 Actions 下 Artifacts（**要登录**、90 天后**过期**）。2026-09-28 因此连着绊了两次。

**做法**：workflow 末尾加一步「刷新『最新构建』预发布版（main 分支）」，
条件是 `github.ref == 'refs/heads/main'`（`master` 也认），把两个包挂到 `latest`
标签下并标成**预发布**。于是：

- 新包永远在 Releases 页面第一眼的位置，**不登录就能下**，也不会过期；
- GitHub 的「Latest」标识仍然归正式版本（`v1.0` 那种），不会被日常构建抢走；
- 版本 Release 的资产仍然只在打标签那一刻定下来，**不会被后续推送悄悄换掉**。

四个实现上的选择：

1. **删掉重建，而不是 `upload --clobber`**：`gh release edit` 改不动 tag 的指向，只覆盖
   资产的话 `latest` 会永远停在第一次那个提交上 —— 别人从 Release 页点「Source code」
   下到的是旧代码，比资产不同步更难发现。所以先
   `gh release delete latest --yes --cleanup-tag`（连 tag 一起删），再
   `gh release create latest --target "$GITHUB_SHA"`，tag 必落在本次构建的提交上。
   代价是下载计数清零、release 短暂消失 —— 对滚动构建可以接受。
2. **`--target "$GITHUB_SHA"`，不用默认分支**：`target_commitish` 允许直接给 commit SHA。
   不给的话 gh 会拿默认分支去造 tag，万一 push 与建 release 之间又插进来一个提交就指错了。
   （这和 1.2 里版本发布用 `--verify-tag` 是同一类考虑：**别让 gh 替你猜提交**。）
3. **`--prerelease` 不能省**：不然它会把「Latest」抢过去，正式版本反而被挤到下面。
4. **标签名选 `latest` 是有讲究的**：版本发布靠 `startsWith(github.ref, 'refs/tags/v')`
   判断，而 `latest` **不以 `v` 开头**，所以它既不会触发版本发布、
   也不会把自己的工作流再触发一遍。

**核对**：

```bash
curl -s https://api.github.com/repos/<owner>/<repo>/releases \
  | python -c "import json,sys; [print(r['tag_name'], 'prerelease='+str(r['prerelease']), r['created_at'], [a['name'] for a in r['assets']]) for r in json.load(sys.stdin)]"
```

应当看到两条：`v1.0`（`prerelease=False`）和 `latest`（`prerelease=True`，时间是最近一次构建）。

## 二、在本机编译（可选）

需要 JDK 17+ 和 Android SDK（platform 36 / build-tools 36.0.0）：

```bash
# 在项目根目录建 local.properties，指向你的 SDK
echo "sdk.dir=/path/to/android-sdk" > local.properties

gradle assembleDebug --offline                          # 产物: app/build/outputs/apk/debug/app-debug.apk
gradle assembleRelease -x lintVitalRelease --offline    # 产物: app/build/outputs/apk/release/app-release.apk
```

（本机一直带 `--offline`：依赖都在缓存里，省掉联网重新解析那一步。去掉也能跑。）

**两个包都要出。** 改完代码只跑 `assembleDebug` 会漏掉 release —— 交付目录里那个 release
会悄悄停在上一个版本，而这次的差异只在图上两个字上，装上基本看不出问题，
但"防伪"这个改动就永远不会到手里。

release 没有开混淆与资源裁剪（`isMinifyEnabled = false` / `isShrinkResources = false`），
也照样用 debug 签名，所以两个包都能直装；体积差（约 8.6MB vs 12.1MB）来自可调试位与
APK 压缩策略，不是代码差异。

**`-x lintVitalRelease` 不要省。** `assembleRelease` 会拉上 `lintVitalRelease` 做全量
Lint 分析，本机实测这一项跑了 **29 分钟还没结束**（debug 构建根本不跑它，所以对比特别刺眼）。
而这个工程里 Lint 配的是 `abortOnError = false` —— 它拦不住任何问题、也不改变 APK 字节，
纯粹让人干等。跳过它 release 构建回到分钟级。真想看 Lint 就单独跑 `gradle lint`。
（历史版本的 release 也不含 Lint 结果，跳过它得到的包与之前一致。）
CI（`.github/workflows/build.yml`）里那条构建命令也带同一个 `-x` —— 两边行为一致，
免得"本机能出、CI 卡住"。

**本仓库没有 Gradle wrapper**（无 `gradlew`、无 `gradle/wrapper/`），所以本地用的是
系统装的 `gradle` 8.14.3（本机路径 `/f/gradle/gradle-8.14.3/bin/gradle`）；
CI 里由 `gradle/actions/setup-gradle@v4` 装上同一个版本（`gradle-version: '8.14.3'`）。
**两边版本一致，所以本机怎么编，CI 就怎么编。**

**JDK 必须钉在 17，而且别指望临时 `export JAVA_HOME`。**

本机的 `JAVA_HOME` 指向的是**另一个 JDK**（实测 jdk-22），用它跑 gradle 会在**配置阶段**
就炸掉，任何 task 都执行不到：

```
Could not configure services using BuildScopeServices.configure().
Caused by: java.lang.ClassCastException: class jdk.internal.loader.ClassLoaders$PlatformClassLoader
  cannot be cast to class java.net.URLClassLoader
  at org.gradle.initialization.DefaultJdkToolsInitializer.initializeJdkTools
```

这报错**长得像 Gradle/AGP 版本不兼容**（`initializeJdkTools` 是 Gradle 内部类，
报错栈里全是 Gradle 自己的东西），很容易误导你去翻 `build.gradle`、降 Gradle 版本。
真因只有一个：**跑 gradle 的那个 JDK 不是 17**。

判据：**7 秒内失败 + 一条 `BUILD FAILED` + 一个 task 都没执行** —— 真编译错误不会这么快。
（`--no-daemon` 救不了：它只是 fork 一个单次 JVM，仍然读 `JAVA_HOME`。）

**这条设置放在用户级，不放在仓库里**：

```
C:\Users\<你>\.gradle\gradle.properties
    org.gradle.java.home=D:/jdk-17
```

为什么要挪出去 —— 它是个**本机专用的绝对路径**，而 `gradle.properties` 是会被提交的。
2026-09-28 就栽在这上面：那一行提交上去之后，GitHub Actions 在
`gradle/actions/setup-gradle` 那一步直接挂了，报

```
Error: The process '/usr/bin/gradle' failed with exit code 1
```

**连编译都没开始**。真因是 Linux runner 上没有 `D:/jdk-17`，gradle 读到这个属性非法后
**连 `gradle --version` 都会立刻退出 1**（本机已复现：`Value 'D:/jdk-17' given for
org.gradle.java.home Gradle property is invalid`）。而 setup-gradle 做版本探测时正好会调一次
gradle，报错于是被包成了上面那句看不出所以然的话 —— 当时我还一度去查"GitHub 是不是被墙了"，
方向完全错了。

所以现在：`gradle.properties` 里**故意不写** `org.gradle.java.home`，并在文件里留了注释警告；
CI 也不需要它（`actions/setup-java` 已经把 `JAVA_HOME` 设成 temurin 17）。
workflow 里还加了一道**守卫**：谁再把 Windows 绝对路径写回 `gradle.properties`，
CI 会在第一步就指名道姓地报出来，而不是甩那句 `/usr/bin/gradle` exit 1。
另加一步「编译环境自检」打印 `java -version` / `gradle --version`，让环境问题一眼可见。

## 三、怎么用

| 位置 | 作用 |
|---|---|
| 顶部左 | **地点**（点击就地修改，超 12 字截断成 `…`）+ 左侧小圆点表示定位状态（绿=已定位／黄=定位中／红=未授权） |
| 顶部右 | 已拍张数、闪光灯开关（见 3.7）、⚙ 设置 |
| 底部左 | 最近一张（点开用系统看图器看） |
| 底部中 | 快门 —— 拍完**自动存到相册** `Pictures/打卡水印相机/`，右下角弹「分享」 |
| 底部右 | 前后摄像头切换 |
| **底部倍率行** | `1x / 2x / 3x …`，点一下就切；在预览上捏合也能连续缩放（见 3.14）。**档位按这台设备的能力现算**，不能变焦的摄像头（含多数前摄）整行不显示 |
| **画面上的水印** | **点地点那行**改地点、**点日期行或卡片里那串时间**改日期时间（见 3.12）；按住会亮一层底 |

> 定位状态一律用短词（`已定位` / `定位中` / `未授权` / `不可用`），状态由左侧小圆点的颜色共同表达
> —— 这行是常驻的，写长了会把地点挤掉。
>
> 顶部栏里**地点胶囊是 `0dp + weight=1`，吃剩余宽度**，右侧三个控件的位置由它们自己决定。
> 早先写的是 `wrap_content + maxWidth=190dp`，地点一长整行的需求宽度就超过屏宽，
> LinearLayout 把 ⚙ 顶到了屏幕外 —— 现象就是「地点长的时候设置图标只显示一半」。
>
> 点水印**空白处**不会触发编辑（浮层直接放行），但也不会点屏对焦 ——
> 预览区现在被捏合手势独占（见 3.14），那个功能一直没实现。

### 3.1 在拍照界面直接填地点

**点水印上的地点行**，或者点顶部左那颗胶囊 —— 两条路开的是同一个弹窗，**不用退到设置页**：

- **手输任意地点**，或者点下拉箭头选最近填过的（自动记住最近 12 个）
- 点「用当前定位反查」调系统 Geocoder 回填地名，回填后还能再改
- 「清空」只清空输入框、**不关窗**（通常是笔误，想重填）
- 确定后**预览上的水印立刻变**，并自动把「显示地点」打开
  —— 否则填了却看不见，只会让人以为没生效

### 3.1.1 地点会自动精简成 `市+区县·小区`

反查几乎不会给你一个能用的地名，它给的是这种：

```
云岭省星海市云山区湖滨街道风和苑3栋2单元501室
```

顶满一行、字号被压小。所以存之前统一过一遍 `Addr.compact`（`Addr.kt`）：

| 输入 | 输出 |
|---|---|
| `云岭省星海市云山区湖滨街道风和苑3栋2单元501室` | `星海市云山区·风和苑` |
| `北京市朝阳区望京SOHO` | `北京市朝阳区·望京SOHO` |
| `上海市浦东新区张江镇` | `上海市浦东新区·张江镇` |
| `星海市风和苑` | `星海市·风和苑` |
| `风和苑` / `DEMO PARK` | **原样返回**（认不出行政层级就别动） |

剪掉的：省（`xx省`／`自治区`）、街道/镇/乡前缀、**居委会层级（`xx社区`／`xx村委会`）**、
楼栋单元室层门牌、括号补充、方位词与「附近」；小区名超过 10 字截断加 `…`。

居委会那一条要**放在楼栋之后**削：`阳光社区2栋3单元501室` 先被削成 `阳光社区`，
此时它后面已经没有字了，就不会被继续削空 —— 整串就叫「阳光社区」的是一个小区名，一个字都不能动。

| `云岭省星海市云山区青溪镇湖滨社区风和苑商业广场` | `星海市云山区·风和苑商业广场` |
| `星海市洛川区阳光社区2栋3单元501室` | `星海市洛川区·阳光社区` |
| `阳光社区` / `幸福村委会` | **原样返回**（整串就是一个名字） |

原则是**只削，不猜**：认不出市/区县层级，且细节一个字都没削掉，就原样返回 ——
宁可长一点，也不能把一个用户没写过的地名编出来。这条有断言看着（`AddrTest`），
网页版同一个函数用 `verify_addr_parity.js` 对拍，两边逐条一致。

**套娃修复**：线上出现过水印显示成 `星海市云山区·云岭省星海市云山区黄…` ——
「上一次的精简结果」被拼上了「这一次的原始长串」。原因是只剥一层行政前缀不够
（串里有两次「省市区县」），以及 `一个特别特别长的小区` 里的「小区」被县级正则
当成了「…区」吃掉了。现在：先按 `·` 切段、末段若能剥出**市+区县两级**就丢掉前面那截，
再**循环剥**行政前缀直到剥不动，并对 `小区/园区/社区/校区…` 这类词尾设了黑名单。
截断会丢信息（所以"一次→二次"允许去掉省略号后重算），但二次之后必然收敛。

### 3.2 横屏

横屏**能用，不是"勉强"**：

- 旋转手机即自动横屏（`fullSensor`，跟随设备方向，不受系统「自动旋转」开关限制）
- 相机画面按 4:3 居中显示，水印浮层**精确贴合画面矩形**（不是屏幕矩形）
- 横屏拍出的照片方向正确（旋转后会自动更新相机 `targetRotation`）
- 顶栏那条地点胶囊和底部提示条**都按屏宽收窄**，不会铺满整宽（见 3.2.1）

**但"横屏长什么样"取决于你是怎么进到横屏的** —— 这一点以前写错了（写成"控件收进右侧竖栏"，
那是只有冷启动才成立的形态）：

| 进入方式 | 用哪份布局 | 长什么样 |
|---|---|---|
| 竖屏打开 → 旋转手机 | `layout/activity_main.xml` | 底部一横排（缩略图／相册／快门／翻转），顶栏在左上 |
| **横着**启动 App | `layout-land/activity_main.xml` | 控件收进**右侧一条竖栏**，顶栏在左上 |

原因是 `MainActivity` 在 manifest 里声明了
`configChanges="orientation|screenSize|keyboardHidden|screenLayout"`：
**旋转时 Activity 不重建，布局也不会重新充气** —— 屏幕上还是竖屏那套 View，
只是被量成了横屏的宽度。`layout-land` 只在冷启动那一次用得上。

**两份布局的代价：id 必须逐一对齐。** 代码只认 id、不认排布，而
`layout-land` 那份**漏一个 id 不会报错** —— ViewBinding 发现某 id 只在部分变体里存在时，
会把生成的字段标成**可空**，主界面于是写安全调用：点下去毫无反应，logcat 也干干净净。
2026-09-28 就栽在这上面：`layout-land` 漏了 `btnGallery`，**横着启动 App 点不到
「从相册加水印」**（旋转进横屏走的是竖屏那份布局，所以只有冷启动才会遇到）。

现在这条缝有三道防线：

1. `LayoutParityTest` 把**两份布局都 inflate 出来**，逐条比对"代码要用的 id"集合。
   它诞生的原因就是上面那个 bug，漏一个当场红。
2. 主界面那句 `binding.btnGallery.setOnClickListener` **故意不写安全调用**。
   两份都有这个 id 时字段才是非空；哪天又只往一份里加东西，**编译就不过**。
3. 每条用例都拿 `topSpacer` 当试纸确认自己真的测到了要测的那份 ——
   只有竖屏那份有它，于是"竖屏该有、横屏该没有"。少了这一步，限定符写错时
   两条用例会双双在测同一份布局、一起绿。

> **横屏版式的既有取舍**：右栏是贴着屏幕右边站的，横屏 4:3 画面居中、左右留黑边。
> 19.5:9 / 20:9 的机器黑边有 150dp 以上，整条栏都在黑边里；
> 16:9 的机器黑边只有 80dp，右栏（120dp，由并排的缩略图+相册决定）会压到画面右缘约 40dp
> —— 这跟倍率行本来就横跨画面右下角（16:9 下压住约 166dp）是同一个量级。
> 真要彻底不压画面，就得把这两份布局**合成一份**（见 §七）。

### 3.2.1 横屏下顶栏胶囊与提示条都不拉满整宽

现象：横屏时顶栏那条地点提示条几乎横贯整屏；底部「已保存到相册」那条也一样，
十几个字挤在正中间、左右各几百 dp 全是空的。

根因是同一个：**这两处的宽度都是"吃满父容器剩余宽度"**（胶囊 `0dp + weight=1`，
Snackbar 默认 `match_parent`）。竖屏 360dp 下看着正常，到 800dp 就变成 680dp 的一条。
再加上上面那条"旋转不重新充气"，**在 XML 里写死宽度对横屏是无效的** ——
所以策略放在代码里按当前屏宽算（`HudSize`），`onCreate` 与旋转回调各跑一次。

| 元素 | 屏窄（手机竖屏 < 520dp） | 屏宽（横屏 / 平板竖屏 ≥ 520dp） |
|---|---|---|
| 顶栏地点胶囊 | `0dp + weight=1` 吃满剩余宽度（**窄屏必须这样**，见下） | `wrap_content` 按内容收，最多 **258dp**；剩余宽度交给新增的 `topSpacer`（`weight=1`），右侧三个控件仍然贴右边缘 |
| 胶囊里的文字 | 由父容器约束，长地址自动省略号 | 最多 **200dp**（12.5sp 中文约 16 个字） |
| 底部提示条 | `屏宽 − 32dp`（≈ 原来），左右各留 16dp | 封顶 **400dp**，左右居中 |

几个不是随手定的数：

- **520dp 门槛是算出来的**：胶囊上限 258dp（文字 200 + 装饰 58）+ 顶栏里除它之外的
  最坏占位约 200dp（两侧内边距 24 + 张数胶囊 80 + 间距 8 + 闪光 38 + 间距 8 + 设置 38）
  = 458dp，取 520dp 留 60dp 余量（张数变三位数也不会顶出去）。
  `HudSizeTest` 里有一条不变量盯着"门槛 ≥ 胶囊上限 + 200"，门槛调低了会红。
- **窄屏不能改成"按内容收"**：LinearLayout 遇到「子项需求宽度之和 > 容器宽」时
  **不压缩前面的子项**，只把后面的摆到容器外 —— 那正是当初「设置图标显示不全」的机理
  （`TopBarLayoutTest` 就是为它写的）。所以窄屏保留吃满剩余宽度那一支。
- **提示条必须在 `show()` 之前改宽度**：Material 在 attach / measure 时还会动这套
  `layoutParams`（让开导航栏的 `bottomMargin`、以及一个"只把上限压更小"的 `maxWidth`）。
  它到底是只改 margin 还是顺带把宽度重置回 `match_parent`，只看代码看不出来 ——
  `SnackWidthTest` 把 Snackbar 真的 `show()` 出来、量过宽度才敢下结论
  （线上表现会是不报错、不打日志的"加了封顶还是满屏"）。

### 3.3 Logo 选不上怎么办（已修）

之前选完图会弹「Logo 读取失败」。**根因是对同一个 URI 开了两次流**：一次 `inJustDecodeBounds`
量尺寸，一次真正解码。相册、云盘、第三方文件管理器给的 `openInputStream` 未必可重复打开，
第二次拿到的是空流 —— `decodeStream` 会安静地返回 null，日志里连异常都没有，所以极难查。

现在改成**只开一次流**：整张图先读进内存，之后量尺寸、解码都在内存里做。
（这也是 `BitmapFactory` 官方推荐的用法 —— `decodeStream` 对不可 mark/reset 的流行为不稳定。）

顺带补的三件事：

| 改动 | 解决什么 |
|---|---|
| 解码优先走 `ImageDecoder`（API 28+） | 能解 **HEIC/HEIF**（现在手机拍照的默认格式，`BitmapFactory` 在部分机型解不出来），并自动应用 EXIF 方向 |
| 强制 `ALLOCATOR_SOFTWARE` | ImageDecoder 默认出 HARDWARE 位图，既不能 `compress()` 成 PNG，也画不到软件 Canvas 上（会直接抛异常） |
| 失败原因分档返回 | 不再只丢一句"失败"，而是明确说：`没有读取该文件的权限` / `打不开这个文件` / `文件是空的` / `图片超过 24MB` / `这个格式解不了（试试 PNG / JPG）` / `写入失败` |

另外还有一个隐性问题一并修了：配置里记着 `logoPath`、文件却被清理软件或卸载删掉了，
会一直"设了 Logo 但照片上没有"。现在读不到就把陈旧路径清掉，不会一直挂着。

选图后的解码也挪到了后台线程，大图不会卡住界面；成功后 toast 里会带上实际像素尺寸。

### 3.5 白色条幅：宽度跟着内容走

参考图里那条白条只到画面中间（约 50% 宽），而旧版是 `w - 2*pad` —— **撑满整行**，
右边留一大块空白，看着像横幅而不是卡片。

现在宽度是算出来的：

```
卡片宽 = 内边距 + 「打卡」标签 + 间距 + 时间 + 间距 + 右侧块(Logo/单位) + 内边距
```

- 右侧块贴的是**卡片右内边距**，不是屏幕右边 —— 卡片短了，Logo 也跟着进来
- 算出来超过 `画面宽 - 2*边距` 时，**先缩时间字号**（68→30，每步 2），而不是让卡片溢出
- 卡片高度同时从 150 压到 116（1080 基准）：150 时白条又高又空，时间字反而显小
- 黄色「打卡」块改成上下各留 8、圆角 11 的近方形块，贴着卡片高度

**后来又收窄过一次**（用户：「不要那么宽」）。卡片是按内容自适应的、没有多余留白，
所以"太宽"只能从各段的尺寸上收。**高度 116 不动** —— 那是照参考图的比例定的
（116/1080 ≈ 10.7%），本来就对；要改的是**宽高比**（4.94 → 4.44）：

| 项 | 旧 | 新 | 1440 宽下省下 |
|---|---|---|---|
| 时间大字基准字号 | 78 | **68** | ≈ 28 px |
| 卡片左右内边距 | 20 | 16 | 10.7 px |
| 标签↔时间 / 时间↔右侧块 | 24 | 20 | 10.7 px |
| 「打卡」标签字号 | 42 | 38 | 13 px |
| 标签左右内边距 | 40 | 32 | 8 px |

```
卡片宽 763.67 → 683.67（-10.5%），占满宽比例 55.7%
```

内容短（没 Logo、没单位）时白条就短，长（带 Logo）时才变长 —— 这是刻意的，
不是"没对齐"。有两条断言钉住这件事（`条幅宽度_*`）：带 Logo 必须比不带宽，
且**都不许超过满宽的 75%**（防以后改回撑满）。

**正文行的两条宽度上界**（`measure()` 里取较小值）：

| 上界 | 1440 宽下的实测值 | 为什么 |
|---|---|---|
| 品牌区左边界 − 间隙 − 边距 | 960.33 | 两块**并排**、底边对齐（见 3.11），不挡就会压到品牌名上 |
| 卡片宽（= 时间条） | 683.67 | 「地点不要超过上面的时间条」—— 用户明确要的 |

```
时间条宽=683.67  行宽上界=683.67  逐行宽=[521.0, 398.0]  品牌区左边界=1016.33
```

第二条只在**卡片真有时间大字**时才算数 —— 关掉时间后卡片会缩到只剩「打卡」标签那么宽
（实测 424.0），照它去卡会把正常的短地名也逼到最小字号。

**放不下时：先小幅缩字号，放不下了才截字。** 顺序不能反。

| 步 | 规则 | 1440 宽下实测 |
|---|---|---|
| 1 | 缩字号，**下限是名义字号的 80%**（`MIN_LINE_SCALE`） | 14 字地名 → 48.0（名义 56 的 85.7%），**一个字不少** |
| 2 | 还放不下就从**尾巴**截到放得下，末尾补「…」（`fitLineText`） | 29 字地名 → 字号 44.8（正好下限），显示 **14 字 + 省略号**，行宽 649 ≤ 683.67 |

- 截尾不截头：地址是层级信息，「省市区街道」决定这是哪儿，「几栋几单元」只是细节
- 标签（`备注` / `打卡人`）不参与截断 —— 截掉了整行就看不出是干什么的
- **能放几个字与出图尺寸无关**：全部尺寸按 `s = 短边/1080` 归一化，1080 宽下也是 14 个字
- 上一版是"0.36 下限 + 缩到放得下为止"，结果 29 字地名被缩成 **22.7px**：字一个不少，
  但小得已经不像水印上该有的字号 —— 用户的原话是「要不就不缩那么小了，小区名字截取几个字算了」

**上界与下限是耦合的**：缩字号是逐磅试到放得下，下限只管"试不动了怎么办"。
卡片再收窄，第 2 步截掉的字数就会变多 —— `超长地点_*` / `只超一点的地点_*` 两条测试钉着这个边界。

配色上「打卡」标签是**琥珀黄底 + 深色字**（`#FFC107` / `#14181D`）。
字必须跟着改深色：黄底上压白字的对比度只有 1.9:1，等于看不见。

### 3.6 地点自动显示（不用每次手点「反查」）

定位到手就自动反查地名并填上。三条约束，缺一条都会出问题：

| 约束 | 为什么 |
|---|---|
| **用户自己填过就不覆盖** | 手输「风和苑」是他要的固定值，不能被自动结果冲掉 |
| **最多自动查两次**（首次定位 + 首次高精度 ≤100m） | 定位每 2~5 秒回调一次，不节流会把系统 Geocoder 拖死 |
| 地名没变不写盘 | 免得白刷一遍 UI |

「谁说了算」用一个 `addrManual` 标记表达，不需要额外的按钮：

| 操作 | 标记 | 之后的行为 |
|---|---|---|
| 手输地点 | manual | 定位变化**不再**自动覆盖 |
| 点「用当前定位反查」 | auto | 仍跟着定位更新（内容是机器给的，不算你的选择） |
| 点「清空」 | auto | 回到自动模式 —— 于是「清空」就是「恢复自动获取」的入口 |

万一 ROM 的 Geocoder 不好使，反查会返回 null，此时保持原样、不编一个地名。

### 3.7 顶部闪光灯开关（三档循环）

顶部栏（横屏是右侧竖栏）有一个闪光灯按钮，单击循环三档：**关 → 拍照时闪 → 补光常亮**。

不做「自动」档 —— 打卡场景要的是确定性：自动档什么时候闪说不准，拍完才发现没闪就晚了。

为什么要三档而不是一个开关：只给「开 / 关」时，用户点了「开」却发现灯不亮，
既无从判断是没生效、没触发，还是硬件本来就没有。常亮档走的是
`CameraControl.enableTorch()`，**和拍照闪光不是同一条底层路径**：

| 档位 | 底层 | 图标 | 现象 |
|---|---|---|---|
| 关 | `flashMode = OFF` + `enableTorch(false)` | 灰色斜杠闪电 | — |
| 拍照时闪 | `flashMode = ON` | 黄色闪电 | 只在快门瞬间亮一下 |
| 补光常亮 | `enableTorch(true)` | 黄色灯泡 | 一直亮着，肉眼立刻可验证 |

- 档位会记住（`Prefs.flashMode`），旧版本的布尔值会迁移过来，不丢用户的选择
- 前置摄像头一般没有闪光灯，这时按钮**置灰不可点**，不会静默失效
- 切换前后摄会重建 `ImageCapture`，所以 `applyFlashState()` 必须在每次 bind 之后重跑 ——
  否则表现为「切一下摄像头闪光灯自己关了」
- 离开界面（`onPause`）会强制关掉常亮档，避免切后台/锁屏后手电筒还亮着

**「点了开、图标亮了、拍照却不闪」是怎么修的**：根因是闪光灯参数只靠 bind 之后的
`imageCapture.flashMode = …` 设置，而部分 ROM 只在 session 配置阶段读一次该参数、
运行时单独 set 不触发 session 重建，参数就白设了。现在改成**两处都设** ——
`ImageCapture.Builder().setFlashMode(…)` 让参数进 session 配置，同时 toggle 后
**重建一次 session** 确保底层真的收到。预览会黑一下，是刻意的：总比「点了没反应」强。

### 3.8 备注与打卡人：为什么要带彩色标签

原来的实现里，这两行都是 34f、常规体、纯白、左对齐，唯一区别只有「打卡人：」这个前缀
—— 在图上根本分不清哪行是哪行，问「备注和打卡人显示在哪里、好像没什么区别」很正常。

现在每行前面加一个**琥珀黄小标签**（`备注` / `打卡人`），正文保持白色：

```
备注      设备运行正常
打卡人    张三
```

标签用的是和「打卡」块同一个黄（`LABEL_BG`），所以视觉上是同一套语言。
「打卡人：」那个硬拼进正文的前缀已经去掉了 —— 它是**标签**，不该变成内容的一部分
（否则用户想改文案时得从正文里把「打卡人：」删掉）。

**另一个坑（这是最初"看不见"的真正原因）**：填了内容**不等于**会显示。
`showNote` / `showName` 默认是关的，两个条件都满足才画。现在改成：
**首次填入内容时自动打开对应开关**（和地点那条逻辑一致 —— 填了却看不见，
用户只会以为没生效）。

只在**从空变非空**这一刻自动开，所以用户之后主动关掉它，下次进来保存不会被重新打开
—— 否则这个开关等于关不掉。

### 3.9 右下角品牌区（三行）与防伪码

右下角三行、右对齐、字号逐行变小（顶部模式时在右上角）：

```
                                        今日水印
                                 相机 ▢真实可验▢
                             防伪 5H3HXQ9UL72SS9
```

第三行的标签是**「防伪」两个字**，不是「防伪码」—— 后面跟的那 14 位就是码本身，
再挂一个「码」字是重复；字号小的时候也少占一个汉字位（约 31px @ s=1.333）。

初版是把品牌名和标语拼成一行、防伪码另起一行 —— 那样读起来是一串没有重点的长字
（`打卡水印  相机真实可验  防伪码 XXXX`）。三样东西性质本来就不同：主标识 / 说明 / 校验码，
分行加递减字号本身就是层级，一眼能分清哪是名字、哪是那串码。

品牌名与标语都能改（设置页），也可以整块关掉。基准字号 **48 / 34.3 / 27.6**（1080 基准），
层级比 1 : 0.714 : 0.575；某一行超宽时**只缩它自己**（下限 0.62 倍且不小于 13s），
层级不会被一张长标语搅乱。

> **行3（防伪码）的字号是从行1 推出来的**，不是另写一个数：
> `BRAND_CODE_EM = NAME_EM × 0.575`。上一轮就是先定 40 再手算 23，
> 两个数各自"看着对"、却没人保证它们还成比例 —— 改一次大小就要记得同时改两处。
> 行2 同理（`SLOGAN_EM = NAME_EM ÷ 1.40`，那个 1.40 是量出来的）。

> **绝对大小不是从参考图量出来的。** 那张 360×165 的裁切只能反解**行与行的比例**
> （1.40，见 `verify/solve_brand.py`）—— 那块裁切在原照片里占多宽，无从得知。
> 所以最初只是沿用了旧版的 30，观感上一直偏小。
> 40 → **48** 是第二次"凭观感"放大（1440 宽下品牌名 64.0，左侧地点 56.0）：
> 品牌区是三行 + 一个灰块，视觉重量本就该压过下面那两行信息一点。
> 行2/行3 同步跟随，层级关系不变。
> 想真正跟官方对齐，需要一张**未裁切的官方样张** —— 手上那几张全是我们自己 App 画的。

#### 品牌名与标语是矢量稿，不是系统字体

这两个词条是**标识**，不是信息。信息（时间/地点/备注）各手机长得不一样无所谓；
标识不行 —— 换个 ROM 换套中文字体，同一张水印就变了样。

所以它们走**轮廓路径**（`BrandMark.kt` + 自动生成的 `BrandMarkPaths.kt`），
跟着 APK 走，与系统装了什么字体完全无关。标语后面那块浅灰圆角底也是稿子的一部分。

| 做法 | 体积 | 结果 |
|---|---|---|
| 塞一份字体进 `res/font` | +1.4 MB | 也一致，但白搭 |
| **只取用到的 10 个字的轮廓** | **+3 KB** | 一致，且不经过字体引擎 |

顺带去掉一整类风险：矢量不会出现「字体没加载上就悄悄退回系统字体」
（PT Mono 那次就是靠 `document.fonts.check` 才发现根本没生效，肉眼看不出）。

**轮廓从哪来**：`Y:\今日水印相机字体\AlimamaShuHeiTi-Bold.ttf` —— 阿里妈妈数黑体 Bold，
阿里官方发布、免费可商用（官网可下载）。选它的依据是**量出来的** ——
参考图里逐字量出的「墨宽/墨高」比与它一致（±4%），并且它是那个目录里唯一覆盖这 10 个字的
TrueType 字（另两个 CJK 是 CFF 的汉仪旗黑，而且渲出来的字重明显偏轻）。
只有这 10 个字的**轮廓**进了仓库（`BrandMarkPaths.kt`，+3KB），字体文件本身没有分发。

**版式参数也是解方程解出来的**，不是目测（参考图只有 360×175，还没我们自己出图的一个字大）。
字体里每个字的墨迹宽高已知，图上量到的是像素，两者一比就得到每行的字号；各字左边界之差
再给出步进。见 `verify/solve_brand.py`：

| 项 | 反解值 |
|---|---|
| 行1 : 行2 字号比 | **1.40**（图上 72.1px : 51.5px） |
| 行1 字距 | **+0.164 em**（这个词条是放松排的，不是默认字宽） |
| 「相机」→ 灰块 间距 | 0.238 em |
| 灰块留白 | 「真实可验」**墨迹框**四周各 0.15 em |

灰块按**墨迹框**算而不是按基线算：按基线算出来的位置与图上差了 9px，
按墨迹框算上下留白才对得上。

**改了名字/标语会怎样**：那一行退回系统字体渲染（矢量稿只做了内置那 10 个字），
设置页的说明里写明了这一点。

**这套稿子怎么从头重做一遍**（换字体、加字都要走这条链，纯 stdlib，不依赖 fontTools）：

```bash
# 1) 探字体：家族名 / 授权 / 覆盖了哪些字，以及是 glyf 还是 CFF
python verify/detect_font.py info  "Y:/今日水印相机字体/*.ttf"
python verify/detect_font.py chars "Y:/.../AlimamaShuHeiTi-Bold.ttf" 今日水印相机真实可验

# 2) 从参考图反解版式：字号比 / 字距 / 灰块留白（解方程，不是目测）
python verify/solve_brand.py

# 3) 提轮廓 → 生成 Kotlin 数据表（顺序不能反，后者吃前者的 _glyphs.json）
python verify/gen_glyphs.py            # → verify/_glyphs.json
python verify/gen_brand_kt.py          # → app/src/main/java/.../BrandMarkPaths.kt

# 4) 闭环：提取出的路径 vs 同字体 fillText，逐像素比（必须 <0.1%）
python verify/gen_glyphs.py && node verify/glyph_parity.js
```

**第 4 步不能省。** 它验的是「轮廓提取器有没有把字读歪」——自己写的 glyf 解析器最容易错在
隐含中点没补、`loca` 基址忘了加、y 没翻转、复合字形没展开，而这些错误**看起来仍然是汉字**，
肉眼逐字比根本发现不了。没有这一步，你可能拿着一份"能画出来但已经变形"的路径跑好几天。

**字形只能取 glyf（二次曲线）的字体**：`0x00010000` / `true` 是 glyf，`OTTO` 是 CFF（三次贝塞尔）。
本机可用的 CJK 里 `AlimamaShuHeiTi-Bold.ttf` 是 glyf；汉仪旗黑是 CFF，而且渲出来字重明显偏轻。

> 生成器只产 `M` / `L` / `Q` / `Z` 四种**绝对坐标**命令，所以 Android 侧不需要通用 SVG
> 路径解析器（也就不需要 `androidx.core.graphics.PathParser` —— 那个类跨版本改过好几次 API）。

**它仍然不能证**「这张照片确实是这台设备的相机拍的」 —— 那需要服务端留底。

**防伪码是真的摘要，不是随机数**：`SHA-256(时间到分钟 + 地点 + 备注 + 打卡人 + 单位 + 机型 + 经纬度)`
取前 70 bit，Base32 成 **14 个连续字符**（与参考图位数一致）。不加分隔横线 ——
横线在水印那种小字号下几乎看不见，却白占三个字符位，抄写时人还会自动忽略它、反而更容易看错。

字符集剔掉了 `0 / O / 1 / I` —— 数字字母混排时这四个几乎必抄错。取整 32 个字符，
正好对上 `& 0x1F`，不留偏分布也不越界。

时间**只取到分钟**：预览是每帧重绘的，若把秒算进去，用户看到的预览码和按下快门后
出图的码会不一样 —— 那才是真的"防伪不了"。

| 它能证什么 | 它不能证什么 |
|---|---|
| 照片上的水印字段**自洽** —— 拿图上的文字重算，能复现出同一个码；谁改过字，码就不对了 | 这张照片**确实是**这台设备在某个时刻拍的 |

后者的原因是校验方没有留底：任何人拿到这些字段都能自己算出同一个码。
真正「可验证」需要服务端在拍摄时留一份摘要存档 —— 那是下一步的事。
在这之前，本地算的这个码是**把这件事提前准备好**，而不是假装已经做到了。
设置页的说明文字只写它能证的，不写它不能证的。

**为什么单独占一段**：试过让它和左侧的地点/备注挤在同一条水平带上（更接近参考图的观感），
但左侧最长那行是地点（42f 粗体）、长备注能到 25 字以上，窄屏上必然撞车 ——
要么给左侧缩字号（伤主体信息），要么把品牌缩到看不清。垂直分开后两边各自完整，
且零碰撞，代价只是品牌行比左侧文字低一点点。

### 3.9.1 编译出来的 APK 里嵌了字体吗

**嵌了一个，65 KB，只给防伪码那 14 位用。品牌区那 10 个中文不是字体，是矢量路径。**

| 内容 | 怎么实现的 | 进 APK 的体积 |
|---|---|---|
| 品牌区「今日水印」「相机 / 真实可验」 | `BrandMarkPaths.kt` 里的**矢量轮廓字符串**（10 个字的 `M/L/Q/Z` 路径） | ≈3.0 KB，在 `classes*.dex` 里 |
| 防伪码那 14 位 ASCII | `res/font/pt_mono_bold.ttf` | 原始 65 396 B ／ 压缩后 36 708 B |
| 中文（地点、日期、备注、标签、品牌走系统字时） | 一律系统字体 | 0 |

直接从两个成品包里读，不用信这段话：

```
python verify/apk_font_audit.py \
    ../watermark-camera-apk/打卡水印相机-debug.apk \
    ../watermark-camera-apk/打卡水印相机-release.apk
```

实测（debug / release 完全一致）：

```
家族名  : PT Mono        子族: Bold        版本: 13.0d2e4
字形数  : 787            码点数: 783       中文字形: 0
fsType  : 0x0000 Installable Embedding（可随产品分发）
判断    : 完整字体，未裁剪
体积    : 原始 65 396 B → 压缩后 36 708 B（占解压后总体积 0.27% / 0.33%）
```

**release 里的文件名不一样，这是正常的，不是包坏了。** 资源压缩会把
`res/font/pt_mono_bold.ttf` 改名成 `res/vj.ttf`，但 `resources.arsc` 里的映射还在：

```
$ aapt2 dump resources 打卡水印相机-release.apk | grep -A1 pt_mono
    resource 0x7f080000 font/pt_mono_bold
      () (file) res/vj.ttf          ← 文件名变了，资源 ID 没变
```

**品牌中文为什么不做成字体**（这是当初的选择，不是漏掉了）：

1. 只取用到的 10 个字约 3 KB，而整包 `AlimamaShuHeiTi-Bold.ttf` 要 1.4 MB；
2. 矢量不过字体引擎 —— 不会出现「字体没加载上、悄悄退回系统字体」。PT Mono 在网页版
   就是靠 `document.fonts.check` 才发现根本没生效的，**肉眼逐字比看不出来**。

**PT Mono 的授权已核实**（`OS/2.fsType = 0x0000`，即 Installable Embedding，字体自带声明
明确允许 bundling with commercial and non-commercial products），许可文本随包放在
`assets/licenses/PTMono.txt`，两个包里都在。

**它不能画中文** —— cmap 里 CJK 区段数为 0。所以品牌防伪码那一行是**分段**绘制的：
「防伪」两个中文走系统字体、后面 14 位走 PT Mono（见 `WatermarkRenderer.BrandSeg`）。

**有两条单测守着这件事**：`等宽字体_PTMono_已加载` 与 `等宽字体_I与M同宽`。
必守的原因是加载失败时代码会**静默**退回系统等宽（不崩、也不出豆腐块），
画面上几乎看不出区别 —— 只有直接问 `Typefaces.mono` 才知道到底加载没有。

**不打算 subset。** 787 个字形里只用到约 40 个，裁完能从 65 KB 降到 4 KB 上下，
但省下的是压缩后 32 KB（release 的 0.4%），代价是多一步构建、多一个可能把
许可文本一起裁掉的坑。不划算。

### 3.10 内置占位 Logo：一份手写的矢量稿

原来没选 Logo 时，卡片右侧永远是空的（回落成单位文字）。但**绝大多数人不会**
为了打个卡先去相册翻一张自己的 logo 出来 —— 所以现在内置了一份**中性占位稿**，
默认就开，装上就带。规则是：

```
用户自选图片  >  内置占位 Logo  >  都没有（卡片右侧回落成单位文字）
```

三个地方查这套优先级 —— 主界面预览、按下快门出图、设置页预览 ——
都走同一个 `LogoStore.pick()`。分开写的话就会出现「设置页看着有、拍出来没有」
这种最难查的不一致。

设置页底下会明写**当前用的是哪一个**（`当前使用：内置占位 Logo` / `自定义图片` /
`不使用 Logo（卡片右侧显示单位文字）`），否则用户分不清是内置生效了还是压根没设上。

**它长什么样**：中性灰蓝（`#3E4C59`）圆角方块 + 白色（`#FFFFFF`）快门环，340×275，
**不含任何公司标识**。选"相机"这个通用意象而不是某个牌子是有意的 ——
内置的只要不丑、不空着就够，谁真要用自己的图，在设置页选一张即覆盖。

**为什么是矢量而不是塞张 PNG**：这份图形是手写的 path，矢量形式只占 **0.5KB**，
而水印画到 1440 宽都不会糊；换成位图要么放大后糊，要么得塞一张大 PNG 把包撑起来。
（`verify/trace_logo.js` 那套"位图 → 矢量"的描摹管线仍然留着 —— 想把自己的位图
logo 描成矢量稿时它能用；但当前内置的这份没走它，是直接手写的。）

同一份稿子要出现在三个地方，任何一处漂了都会表现为「网页版有、安卓没」：

| 位置 | 形式 |
|---|---|
| `watermark-camera/assets/logo-placeholder.svg` | 真源（手写） |
| `watermark-camera/index.html` 的 `BUILTIN_LOGO_SVG` | 网页版内联（单文件可用，不能 fetch） |
| `app/src/main/res/drawable/logo_placeholder.xml` | 安卓 VectorDrawable |

改了图形之后要重跑：

```bash
node verify/inject_logo.js index.html assets/logo-placeholder.svg   # 注入网页版内联
node verify/logo-parity.js gen ../watermark-camera                   # 三处静态比对 + 出探针页
# 再用 Chrome --dump-dom 跑探针页，把结果喂回 check（Node 里 spawn Chrome 会 EBUSY）
```

`verify/logo-parity.js` 静态比对三处：pathData **逐字**相同、viewport 与 viewBox 一致、
填充色与描边色逐条对应、`fill-rule=evenodd → android:fillType="evenOdd"`。
描边那条是新加的 —— 快门环整条都是 `stroke` 画出来的，只比 `fillColor` 等于没比。
之后它还会让 Chrome 真把矢量画到 canvas 上数像素（灰蓝主体、白色快门环、保留透明底）——
矢量"资源在、但画不出来"只有真渲才知道。

**注意**：水印整幅是画在软件 `Canvas` 上的，所以安卓端把 VectorDrawable
**栅格化**成 Bitmap 再用。这里有个坑：别拿 `drawable.intrinsicWidth` 当像素宽，
它带 density 缩放（340dp 在 3× 屏上是 1020px），只拿它算宽高比。

### 3.11 底部对齐：左下正文块与右下品牌区共用一条底边

原来品牌区被摆在正文块的**下方**（`y = 正文块底 + 间隙`），于是「防伪 …」那行比
「2026.09.27 星期日」低一截 —— 看着就是没对齐，用户第一眼就指出来了。

现在底部模式**以 `h - pad` 为共同基线**，两块各自按自己的高度往上让：

```
正文块  [1745.97, 1885.33]     ← h - pad = 1920 - 34.67 = 1885.33
品牌区  [1691.93, 1885.33]     ← 底边严格相等
卡片    [1572.64, 1727.31]     ← 在两者之上，间隔 = GAP_CARD 14s = 18.67
```

代价是两块**落在同一条水平带上**了，于是长地名会直接压到品牌名上 ——
所以正文行多了两条宽度上界（见 3.5），这是同一件事的两半，改一半都不行。

#### 卡片只躲「横向真的撞上」的那一块

卡片贴的是**正文块顶边**（间隔 `GAP_CARD`），而不是"正文顶和品牌顶里更靠上的那个"。

以前一律按 `min(正文顶, 品牌顶)` 让位，等于为一块**不在同一列**的东西白让一次高度：
卡片从左边起、品牌区贴着右边界，正常内容下两者的横向区间根本不重合
（1440 宽下卡片右边界 718.33、品牌区左边界 1016.33，中间隔着 300px）。
实际看出来的间距因此不是 37px，而是 **59px**：

```
卡片底 1686.83 → 正文顶 1745.97    旧：间距 59.14（品牌区比正文块高，把卡片顶上去了）
卡片底 1727.31 → 正文顶 1745.97    新：间距 18.67（正好 GAP_CARD×s）
```

**这两件事一开始是互相打架的**：品牌区字号越大、越往上长，卡片就被顶得越高、
离下面的地点/日期越远 —— 而"品牌区放大"和"卡片贴着文字"是同时要的。
按横向是否重合来判断之后，两者就互不干扰了。

卡片长到真伸进品牌区那一列（超长单位名把卡片撑宽，实测右边界 1405.33 > 1016.33）时，
仍然按老规矩纵向避让 —— 否则白条会压在品牌名上。两条测试分别钉住这两种情况（`卡片_紧贴正文块顶边_*` / `卡片_伸进品牌区那一列时*`）。

**框对齐 ≠ 看着齐**：上面量的是布局框底边。两块字号不同、descent 也不同，
所以字形的**墨迹**底边还会差一点。用 `verify/ink_align.py` 在渲染图上直接数行号：

```bash
python verify/ink_align.py app/build/test-render/A-bottom-text-unit.png \
                          app/build/test-render/G-landscape-bottom.png
# 竖屏：正文块最后一行墨迹下沿 = 1874，品牌区 = 1874  → 差 0 px
# 横屏：1394 vs 1397                                  → 差 +3 px
# （品牌区 30 → 40 → 48 基准，这个差值 5 → 1 → 0 一路收窄）
```

这 0~3px 是字体度量差异（两块字号不同、descent 也不同），不是算错位置 ——
想要"绝对齐"只能让两块用同一个字号，那层级就没了。
品牌区字号越大，这一行越贴近共用基线，所以放大字号顺带把这件事也修好了。

### 3.12 水印上点一下就改：地点 / 日期时间（弹出式）

水印上的地点和时间**本身就是入口**，不用先去顶栏找按钮：

| 点哪里 | 开什么 | 改什么 |
|---|---|---|
| 地点那行 | 地点编辑器 | 手输 / 常用地点下拉 / 用定位反查（和顶栏胶囊同一个弹窗） |
| 日期行，或卡片里那串时间大字 | 日期时间滚轮 | 上排年/月/日，下排时/分/秒 |

滚轮那套用 `NumberPicker`，**一屏六条**：系统只有 `DatePickerDialog` 和
`TimePickerDialog` 两个分开的窗，改一个"日期对、时间也对"的组合要过两道窗点两次确定。
（设置页里那份两步走的入口保留着 —— 它给"顺手改一下"用，不必拨滚轮。）

细节上做对了几件容易漏的事：

- **命中区比看到的放大一圈**（`HIT_SLACK = 12` 基准像素，1440 宽下 16px）。
  小字号下手指差十几个像素太正常，点不中只会让人以为"这功能没有"。
- **只有命中才吃事件**：没命中时 `onTouchEvent` 直接返回 `false`，
  这一下继续落到预览区做点屏对焦 —— 浮层把它吃掉的话预览区就"死"了。
- **按住会亮一层半透明底**（`HIGHLIGHT_BG`）。水印上没有按钮，
  不给反馈就没人知道这里能点。它只出现在预览里：出图走 `ImageWatermarker`，
  那条路不传 `highlight`。
- **点空白处、点品牌区都不响应**。品牌区特意不做入口 —— 用户想点品牌名时
  弹出一个跟品牌无关的编辑器，比不响应更糟。
- **月份/日期/时分秒补零成两位**，否则滚轮里 `9` 和 `12` 混排看着是歪的。
- **改年月会重算当月最大天数**并把日往回拉：否则滚轮能停在「2 月 30 日」上，
  而 `Calendar` 会静默进位到 3 月 2 日 —— 用户看到的和印出来的不是一个日期。
- **滚轮的软键盘被关掉**（`FOCUS_BLOCK_DESCENDANTS`）：滚轮本来就是拨的，
  点一下弹出输入键盘会把整张卡顶上去，还得先收键盘才能接着拨。

弹窗壳是 `CardPopup`（遮罩 + 居中圆角卡 + 标题 + 内容 + 右下角按钮排），
不是 `MaterialAlertDialogBuilder`，原因见 `CardPopup.kt`：两个编辑器要长得一模一样、
按钮要放得下三个、还要点遮罩关闭。

配色上有个**必须写死**的地方：卡片永远是浅底深字，因为它永远压在深色的相机预览上。
所以弹出层单独一套 `Theme.WatermarkCamera.Popup`（**Light**，不跟 App 的 `DayNight` 走）——
跟主题走的话，深色模式会得到"浅底 + 白字"，`NumberPicker` 的滚轮字直接看不见。

键盘还自己躲：`windowSoftInputMode` 那条 `SOFT_INPUT_ADJUST_RESIZE` 在 API 30 起废弃、
本工程又开了 edge-to-edge，API 35 上直接不生效（键盘盖住卡片下半截，「完成」都按不到），
所以改成自己听 IME 的 inset 加在根节点下内边距上（`CardPopup.avoidIme()`）。

### 3.13 边距：一处收窄，三边同时动

`PAD` **一个值管三边** —— 左边正文块的起点、右边品牌区的终点、以及整个下方块的
基线（`h - pad`）。所以「左右再靠边一点」和「再靠下一点」是同一件事，
不是两次改动。

```
PAD  40 → 26（1080 基准）          1440 宽下：53.33 → 34.67
正文块底边     1866.67 → 1885.33   （下移 18.67）
品牌区右边界   1386.67 → 1405.33   （右移 18.67）
```

**不拆成"左右一个、下方一个"**：那就会出现"左右收窄了、底边还在老位置"这种半吊子
状态，而且以后每次改版式都得记住两个数之间是什么关系。

原来那个 40 是照网页版定的，但网页版是**看**的（图片周围本来就有浏览器留白），
相机是**拍**的 —— 成图四周没有留白可言，水印该像官方水印那样压到边上去一点。

连带放松了一条上界：内容区从 `w - 2*40s` 变成 `w - 2*26s`，
所以条幅宽度上限从 1333.33 变成 **1370.67**（时间条实际只有 683.67，够用）。

`PAD` 是 `internal` 而不是 `private`：单测要按同一个数算期望值 ——
测试里写死一份 `40f` 的话，改了这里它不会报错，只会悄悄量错东西。
**同一个理由，卡片内部那几个数也都取了名字**（`CARD_IP` / `CARD_GAP_IN` / `TAG_EM` /
`TIME_EM` / `UNIT_EM` / `MIN_LINE_SCALE`）—— 原先它们是一堆散落的 `40f * s`、`42f * s`，
`PAD` 的注释里只能写一句"这些是别的东西，别跟着改"。现在改哪个、影响哪儿，名字就写着。

### 3.14 相机放大倍数（底部 1x / 2x / 3x …）

预览底部多了一行倍率档位，点一下就切；在预览上**捏合**也能连续缩放。

**档位是按这台设备的能力现算的，不是写死的。** `CameraInfo.zoomState` 给的区间
各机型差得很远 —— 有的只有 `1..4`（纯裁切），有的 `0.6..30`（超广角 + 潜望）。
写死三档的后果：

| 写死的档位 | 在只能到 2x 的机器上 | 在 30x 的机器上 |
|---|---|---|
| 1x / 2x / 3x | 点 3x **毫无反应**（相机直接拒） | 白扔了硬件，永远只用到 3x |

实际算出来的档位（`Zoom.presets`）：

| 设备区间 | 给到的档位 |
|---|---|
| `1 .. 1`、`1 .. 1.2` | **整行藏掉**（≤1.25 视为不能变焦，不白占地方） |
| `1 .. 4` | 1 / 2 / 3 / 4 |
| `1 .. 8` | 1 / 2 / 3 / 5 / 8 |
| `1 .. 10` | 1 / 2 / 3 / 5 / 10 |
| `0.6 .. 8` | 0.6 / 1 / 2 / 3 / 5（**超广角单列一档**） |
| `1 .. 30` | 1 / 2 / 3 / 5 / 10（封顶五档，砍掉的是**上限**那档） |

候选是 2 / 3 / 5 / 10，**不是等比**：2x 人像、3x 近景文字、5x 隔条马路的门牌、
10x 够不着的铭牌。等比会冒出 1.6x / 2.6x 这种说不出干什么用、还占满一行的档。

**两条硬规则**（都有测试盯着）：

1. **任何一档都不许越出相机报的区间。** 比较用精确的 `<=`，**不留浮点余量**：
   上限真报 1.99 的机器若拿到一个 2x 档，点下去 `setZoomRatio(2.0)` 会被相机拒 ——
   而"点了没反应"正是这个功能最不该有的毛病。上限那档**向下**取整到 0.1
   （3.97 → 3.9），下限那档**向上**取整（0.55 → 0.6）。**宁可少一档，不可多一档。**
2. **高亮以相机回调的值为准，不是以我们发出去的值。** 相机会自己改倍数
   （有些 ROM 暗光下往内裁），界面写着 1x 而实际是 1.4x，是最容易出的事故。
   捏出来的值（1.37x）不属于任何一档时**一个都不高亮** —— 假高亮等于告诉用户"你选的是 1x"。

**倍数不落盘，但内存里留着。** 闪光灯档位落盘（那是"设置"：我就要补光），
倍数不落（那是**取景**）：落到盘上会变成"昨天为了拍远处那块铭牌拉到 8x，
今天打开相机对准人，画面糊成一团而屏幕上没有任何东西提示为什么"。
主流相机开相机也一律回 1x。但内存里必须留住 —— 切前后摄、开关闪光灯都会重建
session，不记住就是"换个摄像头刚才的 3x 就没了"。

**捏合是逐次乘增量比**（`zoom * scaleFactor`），不是"起手倍数 × 累计系数"：
`scaleFactor` 是**相对上一次回调**的增量，用起手倍数去乘会得到指数级放大，
一捏直接冲到上限。松手时只吸附**小幅偏差**（±8% 内归到最近档），差得多的原样保留 ——
从 1x 认真捏到 4x 却被拽回 3x 或 5x，用户只会觉得"这下白捏了"。

**预览区因此独占触摸。** 捏合需要**完整的手势流**：DOWN 若不消费，后续
MOVE / POINTER_DOWN 根本不会派发到那个 View 上，表现是"捏合时灵时不灵"。
代价是预览空白处的点击不再往下传 —— 那里本来就没有行为（注释里说的"点屏对焦"
一直没实现）。**将来要做点屏对焦，请加进那一个 `setOnTouchListener` 里，
不要再设一次**：后者会把前者整个顶掉，而且不报任何错。

**布局上没有魔法间距。** 倍率行和操作栏叠在一个竖向 `LinearLayout`（`bottomStack`）里，
位置由操作栏的**实测高度**决定。若改用 `layout_gravity` + 写死的 `marginBottom`，
换台机器（快门高度、导航栏 inset 都不同）不是压在一起就是飘在半空。

### 3.15 出土照片：比例与分辨率（1M / 2M / 4M）

**起因是一句"保存要 3 秒，正常吗"。** 3 秒是结果不是原因，所以先加了一套**分段计时**
（`SaveProfiler`）把链路拆成「解码 / 摆正 / 裁剪缩放 / 水印 / 建条目 / 编码 / 提交 / 缩略图」，
日志长这样：

```
WMCSave 拍照 1152x864 · 0.4s · 1.0MP · 最慢 编码 210ms | 解码=180 摆正=24 裁剪缩放=38 水印=41 建条目=12 编码=210 提交=9 缩略图=6
```

耗时**几乎完全由像素数决定**，所以每条日志必带分辨率 —— 不带分辨率的"慢"是无意义的数字。
量出来是 8MB 一张：`setTargetAspectRatio(4:3)` **不限制分辨率**，CameraX 会挑该比例下的
最大尺寸，16MP 手机存出来就是 8MB。而相册加水印那条路早就有上限（`ImageWatermarker.MAX_SIDE`
的注释写着"再大对打卡照片没有意义"）—— **两边不一致，等于拍照那条路漏了**。

于是把两件事分开交给用户：**比例决定形状，档位决定像素数**。

| 比例 | 1M | 2M | 4M |
|---|---|---|---|
| 4:3 | 1152×864 | 1600×1200 | 2304×1728 |
| 16:9 | 1280×720 | 1920×1080 | 2560×1440 |
| 全屏 | 720×屏 | 1080×屏 | 1440×屏 |

**档位用的是相机上的标准尺寸，不是按像素数硬算的。** 硬算 2M/16:9 会得到 1886×1061
这种零头；1920×1080 人人都认识，投屏、传群、上传考勤系统都不会被挑刺。代价是实际像素数与
标签有 ±10~15% 的出入（1920×1080 是 2.07MP），这在相机行业本来就是惯例。

**「全屏」档的像素是"短边跟 16:9 一样、长边按屏幕比例延伸"。** 全屏在观感上就是
"16:9 再往上多给一点"（20:9 的屏就是 16:9 加上额头下巴），短边保持一致像素数才落在
同一个量级：1080×2400 的屏上 2M 正好是 2400×1080。若改成按长边对齐，全屏/1M 会变成
1280×2844（2.3MP），标签就名不副实了。

**比例是自己居中裁的，不是让相机给的。** 全屏这类档位很多机型根本不暴露
（传感器一般只出 4:3 和 16:9），而且就算暴露也给不出"屏幕的形状"。交给 CameraX 协商，
失败时它**静默退回**一个支持的比例 —— 用户选了全屏却拿到 4:3，而且没有任何提示。
一律按 4:3 采集、裁剪自己做，好处有两条：

1. 结果在什么机器上都一样；
2. **切比例不需要重启相机会话** —— 不闪黑屏、不打断对焦。这一点很值钱。

**取景框就是成品的那一块。** 浮层和 `PreviewView` 摆到同一个矩形（`layoutOverlay` 两处
分开判"要不要更新"，用共同条件提前 return 会让另一块停在错误尺寸），画面用
`fillCenter` 露出同一块居中裁剪区。注意 **`PreviewView` 的 scaleType 枚举里没有
`centerCrop`** —— `fill*` 才是"填满并裁剪"、`fit*` 是留黑边的 letterbox，写 `centerCrop`
会直接资源链接失败。所以黑边里的内容不会被拍进去。

**采样必须两段缩：2 的幂预缩 + 精确缩放。** `inSampleSize` 只能取 2 的幂，源长边 4608 时
只能落到 2304 / 1152 —— **1M（1152）和 2M（1600）会撞成同一档**，用户会觉得"这个设置没用"。
所以 2 的幂只负责粗缩（省内存、省后续耗时），最后一定再走一次精确缩放把尺寸落到目标上。
相册那条路同理：`decode` 的上限给"刚好等于目标"会**缩过头**（4608 → 1152，再回到 1600 就是放大），
必须给两倍。

**判据必须放在裁剪之后。** 4:3 的源裁成 16:9（或更宽的全屏）是**宽留满、高被砍掉约四分之一**，
所以真正先不够用的是短边。只看原图长边算采样倍数，1:1 时代能对、换成全屏之后就错了。

**裁剪必须在摆正之后。** 转 90 度之前裁会把竖图裁成横的。

**小图会被放大，这是有意的。** 1600×1200 选 2M/16:9 时裁完只剩 1600×900，原图就没有
1920 列 —— 只能放大。选择照放大（而不是"缩不上去就把尺寸降下来"），因为用户选的档位、
设置页写的那行「横着拍 1920×1080」都是承诺。但有一条绝不能破：**既然要放大，采样倍数就必须
是 1**，先缩后放是白丢细节。这条由扫描断言钉住（见第五节）。

**「同时保存原图」另存一张同尺寸、同构图、不带水印的**（文件名 `原图_` 前缀）。
默认关 —— 多存一份占用翻倍，只有确实需要的人该打开。三个实现细节：

- **必须先存干净版**：水印是直接用 `Canvas(out)` 画在 `out` 这张图上的（不另拷一份），
  画完就再也拿不到干净版了；
- 两张共用**同一个时间戳**，才能配成 `原图_20260928_130412` / `打卡_20260928_130412` 这一对。
  各自取一次 `Date()` 会差几百毫秒，跨秒就成了两个不同的时刻；
- 原图存失败**不打断流程**（主角是水印图），提示条也只按"真的存上了"才说"另存了原图"。

**默认 4:3 + 1M。** 1M（1152×864，约 0.3MB）认脸、看水印、看环境都够，传群和上传考勤最快。

**档位用显式 `code` 落盘，不用 `ordinal`。** 往枚举中间插一档会让老用户已经选好的档
静默错位；读的时候一律走 `of(code)`，认不出来的野值兜到默认档而不是崩。

**两个值得记住的坑：**

- **`PreviewView` 的 scaleType 没有 `centerCrop`**（见上）。
- **Kotlin 的普通标识符不允许以数字开头**，但允许 Unicode 字母。所以测试方法
  `fun 三档在4比3下的尺寸()` 合法，`fun 2M_4比3_从16MP缩到精准尺寸()` 会报
  `Function declaration must have a name` —— 后者必须用反引号包起来。

## 四、实现要点

- **所见即所得**：预览浮层和出图共用同一个 `WatermarkRenderer`，所有尺寸按
  `s = 画面短边 / 1080` 归一化 —— 预览里水印在什么位置，照片里就在什么位置。
  取**短边**而不是宽度：竖屏时短边就是宽度（与旧版逐像素一致），横屏时若按宽度算，
  水印会被放大近 40%。
- **几何只量一次，绘制 / 命中判定 / 单测共用**（`WatermarkRenderer.measure()` + `place()`）。
  原先 `draw()` 自己量一遍、`drawCard()` 内部又量一遍 —— 两处入参一漂，
  "画出来的卡片"和"测试断言的卡片"就不是同一个东西，而两者看上去都"对"。
  现在 [量] 与 [摆] 各自只有一个实现，`draw` / `hitTest` / `layoutMetrics` 全部走它，
  于是"改了算式不会只改到一半"是结构保证的，不靠纪律。
- **横屏几何换算独立成 `PreviewGeometry`**：传感器吐出的分辨率永远是横向的
  （如 1440x1080），屏幕上显示成 3:4 还是 4:3 由设备方向决定。
  这块是纯函数、有单测，并有「按旧逻辑会算错」的回归护栏 ——
  横屏最容易踩的坑就是拿竖屏比例去横屏容器里算内接矩形，结果浮层变成画面中间一根竖条。
- **无 Google 依赖**：定位走系统 `LocationManager`，反查地名走系统 `Geocoder`。
  不需要 Google Play 服务，国内手机直接用。
- **不联网**：实测 `aapt2 dump badging` 出来的权限表里**没有 `android.permission.INTERNET`** ——
  这个包在系统层面就发不出网络请求。权限是相机、定位、Android 10 以下用的存储写，
  外加一条 `ACCESS_NETWORK_STATE`。
  这条不是我们申请的，是 `androidx.core` / `androidx.lifecycle-process` 的 manifest 合并带进来的
  （`manifest-merger-debug-report.txt` 可查证），只用来读网络状态，**读网络状态 ≠ 能联网**。
  核实命令：`aapt2 dump badging <apk> | grep -c INTERNET` → `0`。
- **拍照流程**：CameraX `ImageCapture` → 按 `rotationDegrees` 转正 → 画水印 → 存 MediaStore。
  存完后图片以 4:3 落在相册里。
- **旋转靠 `configChanges` + 手动更新相机方向**：声明了 `orientation|screenSize` 让 Activity
  不重建（重开会闪一下、状态全丢），代价是没人帮我们更新相机 —— 所以
  `onConfigurationChanged` 里显式把 `Preview`/`ImageCapture` 的 `targetRotation`
  同步成当前屏幕旋转，否则横屏拍出来的照片是横躺的。
- **放大倍数：档位是设备能力的函数，不是常量。** `Zoom` 是纯逻辑（普通 JUnit 跑，毫秒级），
  建按钮的 `ZoomBar` 才碰 View。两条不变式写成了扫描式测试而不是几个例子：
  任何档位都在相机报的 `[min, max]` 内（比较**不留浮点余量**）、严格升序、含 1x、不超过五档。
  详见 §3.14。
- **倍数走 `CameraControl.setZoomRatio`，预览与出图一起变**：zoom 是**相机级**的裁剪区，
  按 CameraX 的契约对 bind 上去的所有 use case 同时生效 —— 所以"预览里看到的取景"
  就是"照片里的取景"，与 `WatermarkRenderer` 那套所见即所得同一条原则。
  水印本身不受影响（它画在成图上，与取景无关），这一点是刻意的：
  **放大倍数是取景，不是水印内容**。
  ⚠ 这一条**只能真机确认** —— 单测跑不到相机，`ZoomTest` / `ZoomBarTest` 验的是
  档位算得对不对、按下有没有反应，验不了"照片是不是真的跟着放大了"。

## 五、怎么验的（不是"应该能跑"）

编译通过 ≠ 画得对，也 ≠ 逻辑对。所以有 **196 个测试**，跑在两种 runner 上：

```bash
gradle testDebugUnitTest --offline
# 产物: app/build/test-render/*.png
```

分两类是**故意的**：

| 类型 | runner | 例子 | 一轮耗时 |
|---|---|---|---|
| 碰 `android.graphics` 的 | Robolectric + NATIVE | 版式渲染、Logo 真渲、布局量坐标、`ZoomBarTest` | 5~13 分钟 |
| 纯字符串 / 纯算法的 | 普通 JUnit | `AddrTest`、`BrandMarkPathsTest`、`ZoomTest` | 秒级 |

理由很实在：解析器、排版算式这类东西改一行就要验一次，塞进 Robolectric
会让每次迭代都等十几分钟 —— 本轮就吃过这个亏（路径解析器出问题时，
要等一整个 Robolectric 类跑完才知道错在哪）。

**二之一、底边对齐 / 宽度上界 / 命中区 / 按下反馈 —— 全是数字**

`layoutMetrics` 一次返回 12 个边界值，`lineWidths` / `lineHitPoints` / `cardTimeHitPoint`
把渲染器**认的那些矩形**原样拿出来：

```
正文块 [1745.97, 1885.33]  品牌区 [1691.93, 1885.33]  卡片 [1572.64, 1727.31]
时间条宽=683.67  行宽上界=683.67  逐行宽=[521.0, 398.0]  品牌区左边界=1016.33
卡片底 1727.31 → 正文顶 1745.97 = 间距 18.67（= GAP_CARD×s，卡片不再为品牌区让位）
行命中点 = [[295.17, 1783.49, 1], [233.67, 1853.17, 2]]   ← 第三个数是行用途标记（1=地点 2=日期）
卡片时间命中点 = [341.83, 1649.97] → DATETIME
[长地名] 正文底=1885.33 品牌底=1885.33    ← 底边对齐在长地名/无卡片/带坐标下同样成立
```

`lineHitPoints` 故意**让渲染器给点**，而不是让测试自己算 `pad + 字号×字数/2`：
自己算的话，量的就不是渲染器判的那块矩形，命中断言会退化成"我算的点在我算的框里"，恒真。

按下反馈靠**两张图的像素差异**判定 —— 半透明的底压在渐变遮罩上，
肉眼看不出"亮了一点"和"没亮"，但差异包围盒能，而且能顺便证明它没糊到品牌区：

```
地点行按下：差异像素=39579  包围盒=(26, 1738)-(563, 1828)      ← 右边界 563 < 品牌区左边界 1016.33
卡片时间按下：差异像素=67156  包围盒=(26, 1564)-(466, 1893)    卡片=[1572.64, 1727.31]
```

第二条的包围盒是**两块并集**：正文里的日期行和卡片里的时间大字是同一个值
（都归 `TapTarget.DATETIME`），点一下会同时亮两处 —— 这是有意的，它们改的本来就是同一个东西。
所以断言写成"上沿不高于卡片上沿、下沿不超过正文块下沿"，而不是"等于卡片那一块"，
免得下一个人把它当成 bug 修掉。

**二之二、矢量品牌稿 —— 数据 6 例纯 JVM + 渲染 6 例真渲**

「今日水印 / 相机真实可验」走的是**轮廓路径**（见前面 §3.9），所以验的对象分三层：

**层一：路径数据本身**（`BrandMarkPathsTest`，普通 JVM，秒级）——
字形数、命令与操作数的配比、轮廓点数、坐标范围、字符集。
这层刻意不碰 `android.graphics`：数据写坏了当场就能发现，
不必等 Robolectric 那十几分钟。

**层二：真渲出来数像素**（`WatermarkRendererTest`）——
灰块的**精确色**像素数、以及块内**深字精确色**像素数：

```
灰块纯色 ≈ 5087 px，范围 x 1213..1404  y 1780..1832   ← 宽 191 ≈ 预期 193
块内深字纯色 ≈ 3478 px                                ← 覆盖率 37.9%，汉字典型值
```

这里**必须用精确色，不能用宽容差**。宽容差会把白字的抗锯齿边缘也算进来
（纯白到纯黑的中性渐变必然穿过浅灰区间），后果是两条断言一起失效：
块范围被撑大（实测 x 从 1207 起，而块真正的左边界在 1266）、
"块内深色像素"混进大片黑色背景（实测 7507 里 5625 是背景）。
数字都很好看，**但一个字不画它也会通过** —— 等于没写。

深字色是带蓝调的 `(38,43,51)`，而白字边缘只能产生灰度（R=G=B），凑不出这个值，
所以这份计数天然不会被白字污染。

**层三：提取器本身的闭环**（`verify/glyph_parity.js`）——
不比字，比像素：把提取出的路径画进 canvas，再把同字体的 `fillText` 画一遍，逐像素相减。
`今日水印` 差 408/1602220 = **0.025%**，`相机真实可验` 差 222/3003890 = **0.007%**，
差异全落在抗锯齿边缘。这层证明的是「提取器没把轮廓读歪」，
与「版式好不好看」是两件事，别混为一谈。

**三、Logo 存取链路 + 内置 Logo —— 13 例**

用 `ShadowContentResolver` 注册自定义流，把「只开一次流」这件事钉死：

```
保存结果: Ok(width=400, height=267), openCount=1      ← 同一个 URI 只被打开了一次
一次性流保存结果: Ok(width=400, height=280)            ← 只能打开一次的 provider 也能存
失败原因: 打不开这个文件 / 这个格式解不了（试试 PNG / JPG）/ 文件是空的
```

内置 Logo 那条链路是**真的把矢量画出来再数像素** —— 「资源在、但画不出来」
（矢量不受支持、比例算错、画成空白）只有真渲才能发现：

```
内置 Logo 尺寸: 400×324                                ← 保持参考图 340:275 的比例
内置 Logo 像素占比: 灰蓝=59.61% 白=8.01%               ← 灰蓝主体 + 白色快门环，不是空白
选Logo的优先级: 自选 > 内置 > 无（关掉内置且无自选 → null，回落成单位文字）
内置Logo开关能存能读
```

**六、顶栏不溢出 —— 4 例真量坐标**

`TopBarLayoutTest` 把界面按 360dp / 320dp 两种屏宽真的 inflate + measure/layout 一遍，
读四个控件的 `right` 边界，断言设置按钮的右边界不出栏 —— 这是"地点太长把 ⚙ 挤出屏幕"
那个 bug 的回归护栏（地点胶囊已经是 `0dp + weight=1`，不再靠 `maxWidth` 硬顶）：

```

栏宽=640 地点右=354 张数右=428 闪光右=520 设置右=612   ← 320dp 窄屏也放得下
```

**六之一、底部倍率条 —— 25 例逻辑 + 2 例真量坐标**

`ZoomTest` 14 例是纯函数（普通 JUnit，毫秒级）：该给哪几档、档位文字怎么印、
高亮认哪个值、松手吸不吸附。分量最重的是那条**扫描式不变量** ——
7 种下限 × 20 种上限共 140 种组合全跑一遍，每一组都验
「档位在区间内 / 严格升序 / 含 1x / 不超过五档」：

```
1 .. 4     → [1x, 2x, 3x, 4x]
1 .. 8     → [1x, 2x, 3x, 5x, 8x]        ← 跳过 4/6/7 这些说不出用途的档
1 .. 10    → [1x, 2x, 3x, 5x, 10x]       ← 上限那档不重复追加
1 .. 30    → [1x, 2x, 3x, 5x, 10x]       ← 封顶五档，砍掉的是 30x 而不是中间的档
0.6 .. 8   → [0.6x, 1x, 2x, 3x, 5x]      ← 超广角单列一档
1 .. 1.2   → 空                          ← 视为不能变焦，整行藏掉
1 .. 3.97  → 末档 3.9x 而不是 4x         ← 越界的档点下去毫无反应，宁可少一档
```

`ZoomBarTest` 11 例走 Robolectric、用真实布局建按钮。两条值得单说：

- **「相机能力没变就不许重建按钮」** —— `zoomState` 是每帧都可能回调的 LiveData，
  捏合时一秒回几十次，每次都 `removeAllViews` + 新建 5 个 TextView，
  既疯狂分配、又会把用户正按着的那一格换掉 —— 表现是「捏合之后点档位经常不灵」。
- **数像素核对胶囊本身**：五格都在、每格 30dp 高、选中那格是纯 `accent`、
  其余是半透明黑压在画面上、整组水平居中。这是「资源写错 / 选了不存在的 drawable /
  背景没生效」这类毛病唯一能自动抓的地方。
  （注意**别断言"首格左边距 = 16dp"** —— 实测 126px = 32 内边距 + 94 居中偏移，
  那条断言会把正确的居中实现误判成 bug。第一版就是这么写的。）

`BottomBarLayoutTest` 里 2 例真量坐标 —— 竖屏五档 + **横屏那份布局**：

```
五档倍率  屏=720x1280 倍率行=0..80 视口=656 档位总宽=468 底栏=80..260 快门=0..152
档位条像素扫描  图=720x80 扫描行y=30 胶囊=126..209 222..305 318..401 414..497 510..593
档位整组居中  左边距=94 右边距=95 内容宽=468 视口=656 共5格
倍率条无障碍描述 = [原始倍率，不放大, 放大 2x, 放大 3x, 放大 5x, 放大 8x]

```

档位总宽 468px（234dp）对 656px（328dp）视口，左右余量 94 / 95（差 1px 是取整）——
**一屏放得下、居中**。五格实测都是 84px 宽（= 42dp 最小宽，`1x`~`8x` 都是两个字符），

外面那层 `HorizontalScrollView` 是兜底，「能拖」不该变成「该拖」；
真要拖才能看全，说明档位给多了，该回去调 `Zoom.MAX_CHIPS`。

横屏那例（上面第 5 行）是**后来补的**：`layout-land/activity_main.xml` 是另一套 XML，
加倍率行时被整个重排过，而在此之前**没有任何测试在看这个文件**。

> **关于 TextView 的字：Robolectric 画不出来（如实记一笔）**
>
> 本想把档位条也渲成 PNG 给人眼看，做不到 —— NATIVE 图形模式能画
> `Canvas.drawText`（水印那 18 张就是走这条路），但 **`TextView` 走的 `Layout.draw` 不落墨**。
> 实测证据：胶囊区域里最亮的像素只到 `(64,68,75)`（= 垫的背景灰 `(42,47,54)` + 12% 浅色），
> 没有任何接近文字色 `(232,236,241)` 的像素；橙格里的深字同理。
> 硬存出来会是「五个空胶囊」，看着像字体丢了 —— 这种图交出去比不交还糟。
> 所以档位条只做像素级断言，**字形好不好看只能真机看**。
>
> 顺带一个坑：`TextView.setTextSize(Float)` 的单位是 **sp**，
> 只有 `setTextSize(Int, Float)` 那个重载才是 px。写错会差一个 density 倍，而且不报错。

**七、防伪码 —— 7 例，含跨实现一致性**

防伪码这种东西最容易"看起来像码就行"，所以断言分成四层：

```
格式     防伪码 = 5H3HXQ9UL72SS9              ← 14 位连排，无分隔横线
字符集   不含 0 / O / 1 / I                   ← 数字字母混排时这四个几乎必抄错
确定性   同输入必同码；改备注/地点/机型就变
稳定性   同一分钟内码不变                      ← 只算到分钟，否则预览与出图的码会不一致
```

**跨实现一致性**是这里最硬的一关：安卓用 `MessageDigest`，网页版是手写的**同步** SHA-256
（`crypto.subtle.digest` 是异步的，没法在每帧渲染里用）。两边独立实现，用同一组输入对拍 ——
网页版算出来的码必须和安卓单测真实跑出来的码**逐字符相同**：

```bash
node verify_brand_parity.js
# SHA-256 长度 55/56/64/119/120/1000B 与 Node crypto 一致   ← 换块边界，补位就错在这附近
# 与安卓版同码 base() + 定位 → 5H3HXQ9UL72SS9
# 与安卓版同码 base() 无定位 → 2SA9N5GMUT7L5R
```

用别人（Node crypto / JDK）的实现当基准，而不是拿自己另一份 JS 自我验证 —— 后者
只是把同一个错误抄了两遍。

> **改基准数据的成本**：种子串里含**地点、备注、打卡人、单位、机型、经纬度**，
> 所以动其中任何一个，上面这两个基准值都会变，`verify_brand_parity.js` 里的
> `want:` 也要跟着换。别把码抄到图上 —— 图上是渲染结果，字号一改就可能被抗锯齿吃掉一位。
> （最近一次就是因为把示例单位名和地名整体换掉，两个值从 `XP6RKVXVBTSQ7M` /
> `XQKXGKJ6Q9Y7TR` 变成了现在这两个。）

**八、内置 Logo 三处一致 —— 静态比对 + 浏览器真渲**

同一份矢量稿要同时存在于三处（真源 SVG / 网页版内联 / 安卓 VectorDrawable），
任何一处漂了都会表现为「网页版有、安卓没」。`verify/logo-parity.js` 分两段查：

```
静态  内联 SVG 与 assets/logo-placeholder.svg 一致
      每条 pathData 逐字相同（换图形时两边各改一半，画出来就是废的）
      viewport 与 viewBox 一致（2720x2200）、viewBox 原点为 0,0
      填充色一致 ["#3E4C59","#FFFFFF"]
      描边色/宽度一致（#FFFFFF / 140）        ← 快门环整条都是描边画的，漏了这条等于没比
      fill-rule=evenodd 已转成 android:fillType="evenOdd"

浏览器  默认(无自选) → 用内置 Logo / 有自选 → 自选优先 / 内置关掉且无自选 → 回落成单位文字
        natural = 340x275        ← 只给 viewBox 时 canvas 画不出（要给 width/height）
        canvas  = 400x324
        灰蓝主体 59.61%  白色快门环 8.00%  不透明 68.0%（保留透明底）
```

安卓端同一张图数出来是 **灰蓝 59.61% / 白 8.01%**，与浏览器的 59.61% / 8.00% 几乎逐位相同 ——
两端各自栅格化，像素占比这种粗指标能对到小数点后就说明画的是同一张。

**九、出土尺寸 —— 26 例纯逻辑 + 7 例真像素（`PhotoSizeTest` / `PhotoSizeBitmapTest`）**

这一层是**唯一需要穷举**的地方：`planDecode` 里"2 的幂先粗缩、再精确缩放"的循环，
边界全在数字上（4608 缩到 2304 还是 1152、1M 和 2M 会不会撞成同一档），
而这些错误到了真机上只表现为"照片比选的那档模糊一点"—— 肉眼根本发现不了。

纯逻辑那 26 例里，值钱的是三条**扫描式不变量**（10 种源尺寸 × 3 比例 × 3 档位 × 2 个旋转 = 180 组合）：

```
① 采样倍数必须是 2 的幂且 ≤ 64
② 裁剪区绝不超出解码出来的图                      ← 超了就是 createBitmap 越界
③ 裁剪区的宽高比贴近目标比例（±0.01）             ← 抓"裁错方向"
④ 既然要放大，采样倍数就必须是 1                  ← 抓"先缩后放丢细节"
```

第 ④ 条是**写测试时才发现的一个真 bug 的前兆**：原先的写法用"短边够不够"判断该不该放大，
1600×1200 选 2M/16:9 时短边 1200 > 1080 看着"够"，可裁成 16:9 后宽度掉到 1600 < 1920，
照样得放大 —— **判据必须放在裁剪之后**，换成"直接比裁剪区与目标"才严谨。

另外两条是**交叉验证**、防"两张表各改一半"：

- 屏幕正好是 16:9 时，全屏档必须和 16:9 档给出**完全一样**的尺寸；
- 全屏档的长边绝不小于短边（喂 0 / 负数 / NaN 也不能，否则 `createBitmap` 直接抛）。

真像素那 7 例起 Robolectric + NATIVE，因为**尺寸断言抓不住"裁的是哪一块"**：
`createBitmap` 的源区域给成从左上角起，所有尺寸断言照样全绿，而用户拍出来会发现每张都偏了一角。
所以用「蓝底 + 正中红方块」取点看颜色：四角必须仍是蓝、中心必须是红；
16:9 砍的是**上下**而不是左右；尺寸已经相等时 `cropTo` 也必须返回新图（`out !== src`），
否则调用方会多回收一次，崩在 `Canvas: trying to use a recycled bitmap`，
离真因很远。

`SaveProfilerTest` 11 例走普通 JUnit，时钟**可注入**（否则真时钟跑起来全是 0ms）。
断言的是会计口径而不是数字：合计是**累计**不是最后一段、最慢取**最大**不是最后一段、
并列时取先记录的、`extra` 为空不留一个孤零零的 `" | "`。
还有一例专门验 `log()` **不抛异常** —— 普通 JUnit 里 `android.util.Log` 是未实现的桩，
调用会抛 `Method i in android.util.Log not mocked`，正好用来证明记账不会把拍照带崩。

**十、HUD 宽度策略 —— 9 例纯逻辑 + 7 例布局实量 + 4 例真 `show()` 出来量**

「横屏时提示条太长了」这类坑的特点是：**它是被"多出来的空间"撑出来的**。
代码里每一行宽度都合理，只有把真实布局按真实屏宽量一遍才看得见。
所以这三层各自管一段，缺一层就有一类错漏能溜过去：

| 层 | 断言什么 | 为什么必须在这一层 |
|---|---|---|
| `HudSizeTest`（纯 JUnit，9 例） | 520dp 门槛两侧各算一次（519dp 还得吃满、520dp 就收窄）；提示条宽度扫全部屏宽都不越界、不为负；外加一条**不变量**——门槛 ≥ 胶囊上限 + 其余控件最坏占位 | 门槛差 1dp 就换一支代码路径，肉眼看不出来；"门槛定低了会把设置图标挤出去"也只能在数字上卡住 |
| `TopBarLayoutTest` 新增 3 例 | inflate 真实 XML、**按横屏尺寸量**：胶囊 ≤ 258dp 且不占半屏、右侧控件仍然贴右边、门槛两侧各量一次 | "撑爆"和"拉长"都是父容器分配宽度的结果，只看代码看不出来（这个测试类当初就是为「⚙ 显示不全」写的） |
| `SnackWidthTest`（Robolectric，4 例） | 把 Snackbar 真的 `show()` 出来再量：横屏不铺满整宽、竖屏两侧留白、收窄后居中、仍在底部 | 宽度是我们**绕过 Material** 塞进 `layoutParams` 的，而 Material 在 attach/measure 时还会动这套参数（bottomMargin、只压小的 maxWidth）—— 是"只改 margin"还是"顺带重置回 match_parent"，只看代码看不出来 |

模拟"旋转到横屏"的关键是：**保持竖屏限定符、只把 measure 的尺寸换成横屏** ——
因为 Activity 声明了 configChanges，旋转时屏幕上还是竖屏那套 View（见 §3.2），
直接给用例加 `land` 限定符会跑去测 `layout-land`，那是另一条路径、测的不是这件事。

**十一、两份布局的 id 对齐 —— 2 例（`LayoutParityTest`）**

这个 App 有两份 `activity_main.xml`（见 §3.2），而**漏 id 不报错**：ViewBinding 会把
只在部分变体里存在的 id 生成成**可空字段**，主界面写了安全调用 → 点了没反应、也没有日志。
`layout-land` 漏掉 `btnGallery` 就是这么发生的，而且**只在"一开就是横屏"时才会遇到**。

所以这个类不看代码、不看注释，直接把两份布局都 inflate 出来，拿
"代码要用的 id"清单逐条 `findViewById`：竖屏那份用 `w360dp-h640dp` 限定符、横屏那份用
`w640dp-h360dp-land`。清单里唯一允许缺席的是 `topSpacer`（横屏顶栏不吃满宽度、
不需要撑杆，代码那边收的是 `View?`）。

两条用例各自带一句**试纸断言**（竖屏该有 `topSpacer`、横屏该没有）——
限定符写错时两条会双双测到同一份布局、一起绿，那等于什么都没测。

## 七、已知限制

- **最低 Android 8.0（API 26）**。Android 10 以下走旧存储路径，需要「存储」权限。
- **用户自选的 Logo 支持 PNG / JPG / WEBP / HEIC**（HEIC 走 `ImageDecoder`，需要 Android 9+）；
  不支持 **SVG**（它是矢量格式，不是位图）和超过 **24MB** 的原图。
  选不上时提示会写明具体原因，不会只说"失败"。
  内置的那份占位 Logo 反而是矢量（编译进包里的 VectorDrawable，用之前才栅格化）——
  这是刻意的不对称：用户从相册里选的只可能是位图，而内置的那份我们自己能挑格式。
- **反查地名依赖系统 Geocoder**。部分设备/ROM 没有地理编码服务，会提示「没查到」——
  此时手填即可，应用不会编一个看起来对的地名。
- **超长地名是"截字"而不是"一直缩"**：先小幅缩字号（最多小两成），还放不下就从尾巴
  截到放得下、末尾补「…」。1440 宽下时间条宽 683.67，能放 **14 个字**；这个字数和出图
  尺寸无关（全部按短边归一化）。所以第 15 个字起就看不到了 —— 想少截字就得让卡片更宽，
  或者把地点写成简称（工位固定的话填一次就会进下拉列表）。
  要彻底解决得**折行**（拆成两行，正文块变高、卡片和品牌区跟着往上让），
  这会改变行数从而动到所有基准值，本轮没做 —— 真遇到了再说。
- **日期时间弹窗的滚轮只改到秒**，没有「昨天/明天」这种快捷档，
  也不改时间格式之外的显示样式（`时间格式` 按钮切的是"含秒 / 不含秒"两档，
  对应已有的 `showSec`；不是任意格式串）。
- **弹出卡片是浅色的、不跟深色模式**。它永远压在深色的相机预览上，
  跟着 `DayNight` 走会在深色模式下变成白纸白字。这是刻意写死的，不是漏了适配。
- **横屏的几何与渲染已验证，但相机取流没上真机跑过**。旋转时相机方向、横屏取景、
  权限弹窗这几条只在代码层面正确。装了之后横屏拍一张，如果水印位置不对或照片躺倒，
  把现象发我。
- **横着开机时，右侧那条操作栏会压到 4:3 画面的右缘一点**（16:9 的机器上约 40dp，
  19.5:9 / 20:9 的机器黑边够宽、整条栏都在黑边里）。它是两份布局里横屏那份的版式
  （见 §3.2），栏宽由并排的缩略图+相册决定（120dp），而 16:9 的黑边只有 80dp。
  这不是漏了适配：横屏的高度预算是硬约束（右栏已经占掉 360dp 里的 334dp），
  再想收窄就得砍快门/翻转的尺寸。真要彻底不压画面，只有**把两份布局合成一份**——
  也就是"旋转进横屏"那个形态（底部一横排）。那会改掉"一开就是横屏"的外观，
  且要一并改掉 `BottomBarLayoutTest` 里"操作栏必须靠右"那条断言。
  2026-09-28 选了「补」而不是「合」：改动最小、不动既有版式；
  漏 id 的老毛病则由 `LayoutParityTest` 从根上堵住了（见 §3.2）。
- 水印**不防篡改**（照片是普通 JPEG，可以 P）。右下角的防伪码只能证明
  「水印字段自洽」（拿图上的文字能重算出同一个码），**不能证明照片是这台设备拍的** ——
  要防篡改得在服务端留摘要做校验，这是下一步的事。别把它当"验真"用。

## 八、和 Web 版的关系

> **状态：网页版已冻结，只做安卓。**
> 下面的对齐关系仍然成立，但**改动只往安卓走**，不再同步回网页版。
> 网页版留着的价值是充当**第二套独立实现** —— 防伪码（手写同步 SHA-256 vs
> JDK `MessageDigest`）和地址精简靠它交叉验证，这是单靠自己跟自己对拍换不来的。
>
> 唯一一次例外：品牌区第三行的标签从「防伪码」改成「防伪」时，网页版**也改了这一个字符串**。
> 它画在同一套版式上，两边文案不一致会让以后的对拍图对不上；一个字符串的同步成本是零，
> 不算"重新做网页版"。

同目录上级的 `watermark-camera/index.html` 是同一个水印版式的单文件网页版，
两者的水印参数是逐条对齐的（`WatermarkRenderer.kt` ↔ `drawWatermark()` / `drawCard()`），
地点精简也是（`Addr.kt` ↔ `compactAddr()`，用 `verify_addr_parity.js` 对拍，21 条用例一致），
防伪码同样（`AntiFake.kt` ↔ `antiFakeCode()`，用 `verify_brand_parity.js` 对拍，
网页版那个手写 SHA-256 与 Node crypto 逐字节一致、算出的码与安卓版逐字符相同）。
内置 Logo 是同一个来源（`LogoStore` ↔ `logoSrc()` / `BUILTIN_LOGO_SVG`，
用 `verify/logo-parity.js` 查三处一致 + 浏览器真渲数像素）。

**两处差异**（都是刻意的）：

| | 安卓 | 网页 |
|---|---|---|
| 归一化基准 | 短边 `s = min(W,H)/1080` | 宽度 `s = W/1080` |
| 防伪码里的机型 | `Build.MODEL` | 空 —— 浏览器拿不到可靠机型 |

第一处：竖屏出图两者完全一致，只有横屏出图时网页版会把水印放大。网页版是竖屏取景优先，不打算改。
第二处：网页版算出的防伪码因此在**真机运行时**与安卓版不同 —— 这本身没问题（它俩本来就是不同设备）。
注意 §五 那两组对拍码之所以能相同，是因为**对拍时两边都把 `deviceTag` 置空**；
别拿真机上的码跨端比对。

改水印样式**只需改安卓**。三个对拍脚本各自会红 —— 它们拿网页版当"另一套独立实现"，
安卓这边参数一变而网页版没跟着变，脚本立刻报不一致。那时有两条路：同步网页版，
或者接受差异并改脚本里的期望值（**后者必须在脚本里写清为什么**，否则下一个人会当成 bug 修）。
